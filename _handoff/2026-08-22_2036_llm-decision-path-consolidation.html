Plan: Chronovisor LLM実行・判断経路の一本化

done plan_0d301bb852814f2a930362020eda87d4 2026-08-22T20:36:35+09:00

目的

  • 本番のモデル選択を [llm.providers.*] と [llm.roles.*] の一箇所に限定し、機能別の旧モデル指定を廃止する。
  • 既存の LLMRuntime、LocalStructuredSession、DecisionRouter、DecisionLaneContract を正規経路にし、同じ責務を持つ迂回路を削除する。
  • 三者合意は維持する。Primary と Challenger を先に実行し、不一致時だけ Tie-break、quorum=2、conservative veto / hold は現行どおりとする。
  • 永続状態へ影響する出力はモデルに完成オブジェクトを作らせず、モデルの選択結果をホストが検証・materialize・sealする。
  • Decision Trace は実行時の正規イベントとreceiptから生成し、Dashboardによる欠損情報の推測をなくす。

やってはいけないこと（必須）

  • Pi、Hermes、DeepSeek Harnessなど、新しいエージェント／ハーネス層を追加しない。
  • 三者合意、quorum=2、mutation veto、no-safe-quorum hold、laneごとの意味論を簡略化しない。
  • LLMRuntimeと同等の新しいFacade、Router、Factoryを作らない。既存基盤で不足する最小APIだけを追加する。
  • 全laneを同じ出力形へ無理に揃えない。永続効果を持たない説明文・分類結果までID化しない。
  • model-eval / adoption artifact用の候補モデル指定と、本番ルーティングを混同して一括削除しない。
  • 互換レイヤーを恒久的に残さない。移行したcallsiteの旧経路は同じphaseで削除する。
  • 本計画の実装と同時に、プロンプト改善、モデル交換、検索品質改善、Dashboardのデザイン変更を行わない。

前提・仮定

  • 調査基準は clean な main / 4c72823。実行開始時に再確認し、driftがあればPlanへ記録する。
  • DecisionRouterの本番経路はすでに classification.primary / challenger / tie_break roleを解決し、旧 DecisionRouterConfig.*_model を上書きしている。
  • Ingest、Recall、Researchの本番モデル選択もrole移行が進んでいるが、live configと一部の評価・補助経路に旧selectorが残る。
  • LocalStructuredSessionはstructured output、repair、監査を担い、既定transportは LLMRuntimeへ委譲している。
  • oMLXとOllamaのadapterは既に同じlocal resource leaseを公開している。新schedulerではなく、既存controlを正規経路から利用する。
  • DecisionLaneContract、schema manifest、effect policy、contract hashは既存の判断契約の正本として維持する。

実行手順

  1. Phase 0 — Baselineを固定する。 HEAD、worktree、live configのmodel selector、全generation roleのprovider/model/revision、direct provider callsite、model-backed lane/schema一覧を採取する。関連pytest、lane-contract corpus、Decision Trace分岐テスト、foreground Recall latencyを実行し、変更前の成功数・pair agreement・unsafe flip・呼び出し数・p50/p95を実行ログへ記録する。
  2. Phase 0 Gate — selectorとcallsiteを4分類する。 各項目を「本番で有効」「既に無効な残骸」「model-eval/adoption専用」「adapter/health/labとして正当」に分類する。分類不能な項目は削除せず、callerまで追跡する。
  3. Phase 1 — 本番モデル選択をroleへ一本化する。 Ingest、Recall、Research、Classificationの本番routeを [llm.roles.*] だけから解決する。live config・tracked sample・docsから旧 [ingest].model、Recall/Researchのmodel selector、production用 [decision_router].*_model を除去する。候補モデルtripletはmodel-eval/adoption専用の入力境界に隔離し、本番loaderへ逆流させない。
  4. Phase 1 Gate — 二重設定が挙動を変えられないことを固定する。 role欠落、capability不足、同一identityの三役割、provider/model/revision不一致はmodel call前にfail closed。本番config内の旧selectorを静かに採用しない。既存テストへ最小のmismatch invariantを追加する。
  5. Phase 2 — model invocationを既存runtimeへ収束させる。 structured callは LocalStructuredSession、非structured generationは LLMRuntime.generate を通す。直接 ollama.chat/generate/embed 等を許すのはadapter内部と明示的なlab/burn/health probeだけにし、productionの例外はcallsite移行と同時に削除する。見た目だけのmodule renameは行わない。
  6. Phase 2 Gate — provider-neutral resource admissionを通す。 LocalRuntimeControl.resource_lease を既存runtimeから最小APIで利用し、LocalStructuredSessionの provider == "ollama" 分岐をlocal provider共通にする。同期Recall等は既存 foreground_lane、backgroundは既存admission/leaseを使う。長いbackground prefill中もforegroundが既存budgetを超えて待たされないことを実測し、backendにないpreemption機構は新設しない。
  7. Phase 3 — 永続効果のmaterialization境界を揃える。 現行Ingestのhost-issued selector → host materializationを参照実装にする。各model-backed laneのschema/effect policyを監査し、ファイル内容、path、mutation配列、apply対象などの効果-bearing fieldだけをhost-issued IDまたはhost-sealed projectionへ置換する。read-only分類やsummaryはそのまま維持する。
  8. Phase 3 Gate — model outputからdurable bytesへ直結できないことを固定する。 quorumはmodelのbounded decision signatureに対して取り、合意後にのみhostが完全オブジェクトを組み立て、再validation、artifact seal、effect guardを行う。affected laneだけcontract/schema policy versionをbumpし、lane-contract caseとadoption evidenceを更新する。unsafe flipは0を必須とする。
  9. Phase 4 — Traceの正本をproducer側へ寄せる。 LocalConsensusAuditStore、DecisionRouter、machine-consensus receiptから、request/role/provider/model/revision/phase/status/contract/artifact/holdを欠落なくtrace eventへ出す。Dashboardは同一requestの正規eventをfoldして表示し、model-backed laneについて processing_activity や複数JSONLから不足フェーズを推測するfallbackを削除する。
  10. Phase 4 Gate — Trace全分岐を固定する。 pair agreement、tie-break quorum、no-safe-quorum hold、artifact seal failure、artifact replay（0 model calls）、単独structured success/failure・non-reasoning bypassをunit/API/実ブラウザで確認する。Artifact → Decision、No quorum → Holdなど既存topologyを変えない。
  11. Phase 5 — 互換コードと設定を削除する。 移行済みselector parser、default model定数、feature wrapper、Dashboard fallback、古いtest fixture/docsを削る。新APIが旧経路を二つ以上消せない場合は追加せず、callsite側の直接利用を選ぶ。production codeの重複が増えたphaseは完了扱いにしない。
  12. Phase 5 Gate — 静的inventoryを0または明示allowlistにする。 productionからのdirect provider call、[llm.roles.*]外のgeneration model selector、独自structured repair、model-authored durable payload、Dashboard semantic fallbackを rg とテストで検査する。allowlistには理由と削除条件を残す。
  13. Phase 6 — 全検証、commit、必要時のみdeployする。 各phaseを独立commitし、targeted suite、ruff、mypy、隔離rootで全pytestを通す。pushは明示依頼がある場合だけ行う。deploy時はlive configをrole-onlyへ原子的に更新し、push → service restart → archive commit → health → live route/Trace/Recall確認の順で照合する。
