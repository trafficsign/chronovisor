目的

  • Chronovisor の main 推論を JANGQ-AI/Qwen3.8-Flash-Next-JANG_4S / vMLX へ恒久切替する。
  • 現行 Jundot/Qwen3.8-Flash-Next-oQ4e-mtp を fallback・常駐・モデル登録から除き、不要な実体を回収する。
  • Recall 用 Ornith など main 以外の既存役割を維持し、再起動後の実処理とメモリ改善を確認する。

やってはいけないこと（必須）

  • 無関係な dirty worktree、他モデル、Chronovisor データを変更・削除しない。
  • 新 main の live acceptance 前に現行Qwenのモデル実体を削除しない。
  • 認証情報を成果物、ログ、commitへ含めない。
  • 一時的な手動プロセスだけで完了扱いせず、ログイン後も再現する管理サービスにする。

前提・仮定

  • 前段ベンチ fd724f9 により、JANG_4S は Chronovisor 19 lanesで現行と同じsemantic score、clean-load resident 25.3%削減を確認済み。
  • oMLX は Ornith の実行基盤として残し、現行Qwenだけを外す。
  • production config・service contract・全consumerを確認してから最小差分を決める。

実行手順

  1. Git、設定、モデル登録、サービス、ディスク、プロセス、swapの切替前状態を固定する。
  2. main model設定のproducer/reader/consumerと既存service管理経路を確認し、変更範囲を確定する。
  3. JANG_4S/vMLXを恒久パスと管理サービスへ昇格し、起動・停止・自己診断を実装・検証する。
  4. Chronovisorのmain routingをJANG_4Sへ変更し、現行Qwen fallbackを設定から除く。
  5. 関連サービスを安全に切り替え、health・structured decision・実consumerをlive検証する。
  6. 現行Qwenの登録・常駐・モデル実体と不要な一時環境を削除し、ディスクとメモリを確認する。
  7. 再起動耐性、Chronovisor各サービス、oMLX Ornith、設定read-backを最終確認する。
  8. 証跡とPlanを完了し、対象差分だけcommitする。

  • Chronovisor mainの実効endpoint/modelがvMLX/JANG_4Sで、旧Qwenへのfallback参照がない。
  • JANG_4S serviceが管理下で自動起動し、API healthとstructured outputが成功する。
  • 旧QwenはoMLXで未登録・未ロード、モデル実体も削除済み。Ornithは引き続き利用可能。
  • Dashboard、LAN、Semantic、Reranker、Ingest等が健全で、メモリ改善を観測できる。

  • 設定の静的検証、既存関連tests、service lifecycle self-checkを通す。
  • 新serviceのhealth/models/chat、Chronovisor schema decision、実consumer receiptを確認する。
  • stop/start後も同一endpoint/modelへ復帰し、旧モデル参照・process・open fileが残らないことを確認する。
  • 最終のresident/footprint/swap、Dashboard 200、LAN TLS 401、Semantic/Reranker readyを保存する。
