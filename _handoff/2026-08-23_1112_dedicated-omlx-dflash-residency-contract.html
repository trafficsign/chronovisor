実装契約書: oMLX / DFlash2 モデル専用隔離・TTL residency

done plan_11b161cfc573491b8d1d8204aa26c5cb 2026-08-23T11:12:17+09:00

目的

  • Qwen3.8 と Muse が同一 oMLX プロセス内で交互に DFlash runtime を奪い合う状態を止める。Museのモデル本体・draft model・DFlash prefix cacheは専用8002のrequest burst中に保持し、idle時はnative TTLで安全に解放する。
  • 分類モデル、処理順、Decision Trace、構造化出力契約を変えずに、モデル再ロード待ちだけを除去する。
  • 128 GB unified memory 内で長文 prefill の一時メモリを残せることを実測で証明し、危険ならトラフィック切替前に中止できる実行手順にする。

固定する最小構成: 8000 = Qwen3.8 + Ornith + bge、既存 8001 = Gemma、新規 8002 = Muse。Chronovisor からの生成は既存の process 間共通 model_resource_lease で直列のままとする。

契約判断

論点決定理由
高速化方式DFlash モデルを別 oMLX process に隔離し、Muse は native TTL で需要時だけ保持DFlash runtime hooks/cache は process-global。永続3モデル常駐はswap gateに2回不合格だったため、process分離は維持しつつidle時のMuseだけをoMLX自身に解放させる。
モデル現行 Qwen / Muse / Gemma を維持小型モデル化による品質低下を持ち込まない。
実行順現行順序・直列 lease を維持Decision Trace と unified-memory peak を変えない。
DFlash L1 cache各モデル 2 entries / 2 GiB のまま実装上の hard byte cap があり、増量の根拠となる hit rate はまだない。
SSD L2 cachepilot では無効RAM 問題の解決にはならず、I/O・SSD wear・障害面を増やす。
mlx-dspark本番 backend に採用しない現行 oMLX の Qwen 実測と速度差がほぼなく、Chronovisor が使う embeddings / JSON schema API の drop-in replacement ではない。
DashboardModel Fleet の endpoint 集約だけ変更UI・Decision Trace は触らず、3 process の実状態だけ正しく表示する。

やってはいけないこと（必須）

  • classification / research / librarian / recall の段階、lane 順、Primary / Challenger / Tie-break のモデル、revision、reasoning 設定を変更しない。
  • stage batching、最大50件化、複数 DFlash 推論の同時実行をこの変更へ混ぜない。別実験で扱う。
  • src/chronovisor/core/omlx_adapter.py や lease 実装を、再現テストで既存機能の不足が証明されない限り変更しない。複数 endpoint routing は既に実装・テスト済み。
  • L1 cache を 2 GiB/model より増やさない。SSD L2、TurboQuant KV、context window、sampling 値を変更しない。
  • モデル weight を複製しない。新しい base path も /Users/trafficsign/.omlx/models を共有する。
  • oMLX の settings.json にある credential / secret を repo、handoff、ログ抜粋、commit へ入れない。
  • dirty worktree の無関係な変更を触らない。rollback に git reset --hard や broad delete を使わない。
  • 明示された push 権限がない状態で push、GitHub-backed runtime restart、live cutover を行わない。

確認済みの前提・根拠

  • /Users/trafficsign/.omlx/logs/launchd-stderr.log:20713 以降に because dflash runtime hooks/cache are process-global と Qwen ↔ Muse の相互 unload が反復している。
  • 同ログの load estimate は Qwen 24.90 GB、Muse 25.02 GB。Gemma process のログは約 15.00 GB。Ornith + bge は status estimate で約 6.5 GB。
  • 現 process 観測窓では Qwen load 22回、Muse load 23回、model-loading stall 合計は約576秒。実装セッションは切替直前に同じ集計を再取得し、baseline artifact として残す。
  • /Users/trafficsign/.omlx/model_settings.json:26-32,90-94 と Gemma 側設定で L1 は有効、各 max_entries=2、max_bytes=2147483648、L2 は無効。
  • DFlash L1 実装 .../dflash_mlx/cache/prefix_l1.py は挿入後に entries と snapshot.nbytes 合計の両方を検査し、上限以下になるまで eviction する。単一 snapshot が 2 GiB を超えれば挿入した本人も eviction され、保持されない。
  • snapshot.nbytes は FA KV、GDN state、draft context、logits、sidecar array を加算する。ただし Python object、allocator fragmentation、実行中 request の live KV/prefill allocation は cap 外なので、2 GiB は process 全体の上限ではない。
  • 2026-08-23 11時台の平常 baseline は swap used 346.88 MiB、memory_pressure -Q の free percentage 91%。oMLX が示した effective memory ceiling は約 105 GiB。
  • OMLXAdapter は endpoint ごとの runtime を既に構築でき、DFlash request は process 間共通 lease を取得する。tests/test_omlx_adapter.py::test_config_routes_distinct_local_omlx_servers が既存契約。
  • Dashboard の src/chronovisor/ops/dashboard.py::_omlx_snapshot() だけが現在 OMLX_BASE_URL 1件を直接参照するため、Model Fleet のみ小さな集約修正が必要。Decision Trace の data path とは独立している。

回答: 現在の cache 設定そのものはメモリ的に制御可能。3 process 全部を満杯にしても cache は最大6 GiBで止まる。危険要因は cache より、3モデル常駐に長文 prefill の一時 allocation が重なること。永続常駐は実測gateで棄却し、cutoverは専用8002のnative TTL、active-request保護、反復load/unload後のswap非増加を条件とする。

  • 永続常駐案の合格条件（不合格確定済み）: warm-up 後の steady footprint が 85 GiB 以下、effective ceiling まで20 GiB以上の余裕、swap 増分1 GiB以下、memory pressure normal。
  • 共通の即時中止条件: footprint 90 GiB超、swap 増分4 GiB超、free percentage 10%以下が60秒継続、Metal allocation error / process kill、同等 workload で generation throughput が15%以上悪化。
  • cache efficiency は成功条件の主目的にしない。現在値は約0.5%であり、prefix 再利用が少ない workload では cache を残しても速くならない。まず model swap 消滅を評価する。
  • 専用化後も hit rate が5%未満なら2 GiBのまま、または縮小候補。10%以上かつ prefill wall time 改善が再現し、24 GiB以上の余裕がある場合に限り、別契約で4 GiB/modelまで検討する。

実行手順

  1. 実行権限と作業状態を確定: repo status、branch/worktree、HEAD、local-only commit、稼働中 service、runtime archive commit を記録する。push/restart権限がなければ live config は触らず、repo 実装・commit 後に blocked とする。
  2. baseline を固定: 同じ代表 prompt/output 条件で Qwen/Muse を交互に最低12 request実行し、wall time、prefill TPS、generation TPS、load count/load seconds、cache hit/cached tokens、oMLX memory、memory_pressure -Q、sysctl vm.swapusage を保存する。開始・終了log offsetも残す。
  3. repo の最小修正を test-first で実装: _omlx_snapshot() が configured kind="omlx" endpoint を一度ずつ読むようにし、同じ model id は1行へmergeする。いずれかの endpoint で loaded=true なら loaded row を優先。1 endpoint failure は他 endpoint の正常表示を潰さない。UI HTML、Decision Trace、route order code は変更しない。
  4. targeted/full test: multi-endpoint merge、partial failure、既存single-endpoint fallback、OMLXAdapter、Decision Trace orderを通す。続いて隔離rootでfull suiteを実行する。失敗を既存不具合として無視しない。
  5. repo変更をcommit: 差分が許可2 fileと必要な非秘密evidenceだけであることを確認し、意味のある単位でcommitする。明示権限がある時だけpushする。
  6. Muse base path を作成: .omlx-gemma の最小構造を踏襲し、.omlx-muse/settings.json は loopback:8002、共有model_dirs、現行balanced memory guard、global idle timeout nullとする。model_settings.json は Muse の現行DFlash設定とfallbackで追加したper-model TTL=60だけを持ち、L1=2 entries/2 GiB、L2=false。credentialは既存local値を安全に移し、mode 0600、証拠からredactする。
  7. LaunchAgent を追加: label com.trafficsign.omlx-muse、base path/working directory/log path を .omlx-muse に向け、mainと同じpatched runtimeを使う。model weightは共有し、複製しない。load後、8002の認証境界とhealthを確認する。
  8. トラフィック前 memory gate: Museだけを8002へwarmし、既存Qwen/Gemmaもresidentにする。15分の直列long-prefill probeで85/90 GiB、20 GiB headroom、swap、pressure、errorの閾値を判定する。不合格ならconfig変更前に8002をbootoutしrollbackする。
  9. role routing を切替: omlx_muse providerを追加し、上記6 roleだけを8002へ変更。全route manifestを出力して、Primary/Challenger/Tie-breakの順序とmodel/revisionが同一でendpoint hashだけ変わったことを比較する。
  10. 正しい順でlive反映: pushが許可されている場合は push → Chronovisor restart → runtime archive commit確認 → health → live browser/API の順を守る。GitHub-backed uvx をpush前にrestartしない。
  11. post-runを実施: baselineと同じ12件以上の交互request、同一prefixの再利用probe、30分の実workloadを実行する。3 processのlogでcross-model unloadが0、各DFlash model loadが原則1回、memory gate継続合格を確認する。
  12. Dashboard/live acceptance: Model Fleetに各modelが重複なく出て、request burst中はQwen/Muse/Gemmaが同時loaded、idle TTL後はMuseだけunloadedへ戻ることを確認する。Decision TraceのDOM順・badge・model名・最終結果がbaselineと同一であることを実ブラウザ、API、console、service healthで照合する。
  13. 契約を完了更新: 証拠path、commit、push/runtime archive（実施時）、測定差分、rollback可否を実行ログへ追記し、全完了条件を満たした時だけstateをdoneにする。

Rollback

  1. 6つのMuse roleをprovider omlx（8000）へ戻し、route manifestがbaselineと一致することを確認する。
  2. live反映済みなら通常のrevert commitをpushし、同じ push → restart → archive → health → live 順で戻す。hard resetは使わない。
  3. launchctl bootout "gui/$(id -u)/com.trafficsign.omlx-muse"。plistと.omlx-museは即削除せずtimestamp付きbackupへ移し、復旧可能にする。
  4. 8000/8001、Dashboard、ingest、Recall、Decision Traceのhealthを再確認する。page/raw artifactのmigrationはないためdata rollbackは不要。

継続実行: memory gate再判定とadaptive fallback

  1. 測定境界を修正: process開始前、各model warm-up直後、post-warm基準点、steady workload中を分離し、一回性page-outと継続swap増加率を別々に判定する。
  2. 専用Museを再pilot: backupから8002を回収可能に復元し、route未変更のままsegmented memory gateを完走する。不合格時は即rollbackする。
  3. 代替実装を完遂: 厳格なabsolute swap条件が専用常駐を拒否したため、oMLX native ttl_seconds=60 とactive-request保護を利用する。2 cycle、60秒超request、idle unload、swap非増加を実機確認済み。custom LLMRuntime residencyはnative機能で不足が再現するまで追加しない。
  4. production acceptance: 6 role、route順、model/revision、structured output、Decision Trace、shared leaseを維持し、push後restart、archive、health、post-run、実ブラウザを照合する。
