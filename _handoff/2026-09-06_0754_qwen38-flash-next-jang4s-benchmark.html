Plan: Qwen3.8 Flash Next JANG_4S 実機ベンチマーク

done plan_36a34504b3fd4042a9392cc5e9b50d44 2026-09-06T07:54:15+09:00

目的

  • 現行 Jundot/Qwen3.8-Flash-Next-oQ4e-mtp（oMLX）と候補 JANGQ-AI/Qwen3.8-Flash-Next-JANG_4S（vMLX）を同一 Mac・同一プロンプトで比較し、Chronovisor の主モデルとして実用になるか判定する。
  • 品質、構造化出力、実データ再生、短・中・長文脈の速度、常駐/ピークメモリを分離して測る。

やってはいけないこと（必須）

  • 本番設定やモデル割当を変更しない。
  • ユーザーの無関係な dirty worktree を変更・commit しない。
  • 認証情報をログ・成果物へ書き出さない。
  • 計測後に、停止前に動いていた Chronovisor / 推論サービスを戻さないまま終えない。

前提・仮定

  • 候補は vMLX 向けの JANG_4S とし、現行は現在の実運用 oQ4e-mtp/oMLX を基準にする。
  • 候補の gated repository へ現在の Hugging Face 認証でアクセスできることを前提とする。
  • 既存の汎用ベンチマークと Chronovisor の replay corpus を再利用し、新しい評価基盤は作らない。

実行手順

  1. 停止前の Git・ディスク・メモリ・プロセス・launchd・モデル状態を記録する。
  2. JANG_4S の取得可否とファイル実体を確認し、隔離した vMLX 実行環境を準備する。
  3. 既存ハーネスと Chronovisor replay corpus から同一評価セットを確定する。
  4. Chronovisor の関連サービスを停止し、メモリが落ち着いたクリーン状態を確認する。
  5. 現行 oQ4e-mtp/oMLX を品質・文脈長・速度・メモリで計測する。
  6. 候補 JANG_4S/vMLX を同条件で計測する。
  7. 結果を照合し、Chronovisor 採用可否と犠牲になる項目を判定する。
  8. 停止前のサービス状態を復元し、API・モデル・プロセスを確認する。
  9. 証跡と結論を保存し、計画書を検証して完了状態にする。

実行中更新ルール

  • 実行手順のチェックは、各手順の完了直後に更新する（まとめて更新しない）。
  • チェックを更新したら、同時に 実行ログ へ時刻付きで追記する。
  • 中断時は 状態（plan-meta の JSON および .badge の data-state）を blocked にし、理由を ブロッカー に記入する。

完了条件

  • 両モデルの同一ケース結果、文脈別レイテンシ/スループット、ロード後/ピーク RSS、失敗内容が保存されている。
  • JANG_4S が現行比でどの品質・速度・メモリを得失するか、Chronovisor の用途に即して結論が出ている。
  • 停止前に稼働していたサービスが復元され、現行モデルの応答を確認できている。

検証手順

  • ベンチ JSON をスキーマ・ケース数・エラー数について機械確認する。
  • 候補の API health、構造化 JSON、長文脈、MTP 動作をログと応答の両方で確認する。
  • 復元後に launchd/process、oMLX health、Chronovisor health を停止前スナップショットと照合する。
