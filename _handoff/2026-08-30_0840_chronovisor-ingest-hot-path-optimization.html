Plan: Chronovisor Ingest Hot Path 最適化

ready plan_71cea22bf5304670b3aabeaeedacfa71 2026-08-30T08:40:14+09:00

目的

  • Qwen3.8-Flash-Next-125B が応答を返した後、次の処理へ移るまでのホスト側待ち時間を除去する。
  • モデル生成時間を除く ingest のホスト側クリティカルパスを、通常の1ページ変更で p95 10秒以内、無変更で p95 1秒以内にする。
  • 重複判定、ページ同一性、曖昧時の fail-closed、strict semantic publication、read-back を一切弱めず、現在と同じ判断結果をより少ない処理で得る。
結論: LLMは止まっていない。遅延の主体は、LLM応答後の全ページ反復読込と、成果物確定後のCPU 1件ずつ埋め込みである。全ページ照合はprocess起動・障害復旧・明示rebuild時だけに限定し、通常のingestでは既存のwrite receiptから変更ページだけを IndexStore へ反映する。新しいキャッシュ基盤は作らず、既存storeと既に常駐しているMPS前景埋め込み経路を再利用する。

  1. 全ページ照合は起動時だけ: process bootstrapで IndexStore.refresh() を1回実行してbaselineを確定する。通常のtriage、validation、apply後、read-backでは all_pages()、_scan_disk()、full refresh() を呼ばない。crash recovery、明示rebuild、検出不能な外部変更の復旧だけを例外にする。
  2. 全ページ再読込をゼロ化: triage() のfolder/countは既存の IndexStore.all_canonical_page_keys() と page_count() から得る。_find_page_casefold() とloose一致も all_page_ids() / meta() 上で行い、最後のcanonical path検証は残す。
  3. 同じ判断を一度だけ: _triage_plan_validation_issues() 内で同じoperationのeffective targetをリクエストスコープのdictにmemoizeする。グローバルcacheや新DBは作らない。
  4. write receiptで差分反映: ingestが既に返す created/updated page idとprepared pathを正本receiptにし、既存 IndexStore へ最小の apply_changes(upsert_paths, removed_page_ids) seamを1つだけ追加する。変更ファイルだけをstat/parseし、canonical entries・backlinks・associations・generationを同じmutation境界で更新する。通常ingestにdeleteはないためremoveは既存の削除writerが必要になった時だけ使う。
  5. 同期失敗はfail closed: page本体のcommit後にstore差分反映が失敗した場合、成功したふりをして古いsnapshotをread-backしない。indexをdirtyとして当該jobをrecoveryへ送り、対象receiptの再適用、なお不明ならhot path外のfull reconcileで回復する。
  6. strictだけMPS fast lane: index_pages(wait=True) のdocument embeddingだけ、既存の _embed_foreground_documents() を使う。これは既にmodel lock、accelerator lease、source classification、document purpose、MPS self-testを持ち、maintenance batch 32を利用できる。wait=False のbackground workerは現在のCPU経路を維持する。
  7. 見えない待ちをなくす: 新しいSVG topologyは作らず、既存のruntime status / console eventに target-resolution、semantic-publish、read-back と経過msを出す。500ms超の空白は必ず名前付きstageとして見えるようにする。

検討した案と判断

案判断理由
read-backを非同期化して次rawを先に進める不採用速く見えるだけで、semantic delta未公開のまま次処理へ進み、過去に起きたfalse missを再導入する。
全ページ用の新cache / DBを追加不採用IndexStore が既に同じ責務を持ち、現コーパス5,535件を欠落なく保持している。
変更後にfull IndexStore.refresh()を1回だけ実行不採用回数は減るが、1ページ変更のたびに全5,535ページの列挙・statが残るため。
既存write receiptから対象entryだけ更新採用writerは変更したpage id/pathを既に知っている。新しいjournalやcacheを作らず、処理量をO(全ページ数)からO(変更ページ数)へ落とせる。
重複候補をtop-kだけに限定不採用品質と重複防止の意味を変える。全候補比較は残し、データ供給だけをdisk parseからmemoryへ変える。
CPU batchだけを1→8/16へ変更fallback改善はするが、CPU modelのcold loadと二重常駐を残す。MPS gate不合格時のみ実測最速値を選ぶ。
strict MPS、background CPU採用既にwarmな同一model・同一document encoderを再利用し、正本deltaとbackground耐障害性を両立する。
ANE / CoreMLへ新規移植今回不採用現在のSentenceTransformers/PyTorch backendにANE routeはない。CoreML変換は単なる設定変更ではなく、新model artifact・新runtime・新parity責務を増やす。実装開始時に既存のローカルANE対応artifact/backendが存在するかだけ確認し、存在しなければN/Aで終了する。

やってはいけないこと（必須）

  • Qwen3.8-Flash-Next-125B-oQ4e-mtp、port 8125、context、MTP、single-authority構成をこの作業で変更しない。
  • 重複判定のscore閾値、SequenceMatcherによる全候補比較、alias順序、case/Unicode/loose一致、曖昧時fail-closedを弱めない。
  • strict semantic publicationまたはread-backをfire-and-forgetへ戻さない。
  • 通常のingest前後に all_pages()、_scan_disk()、full IndexStore.refresh() を呼ばない。「1回だけならよい」として戻さない。
  • 新しいcache database、queue、feature flag、抽象interface、model copy、CoreML変換物を追加しない。
  • background CPU indexingを根拠なくMPSへ全面移行しない。同期critical pathだけを対象にする。
  • ユーザーの未完了差分 scripts/recall_r6_harness.py、tests/test_recall_r6_harness.py、_handoff/evidence/2026-08-29-recall-teacher-salvage/ に触れない・commitしない。
  • ベンチマークのために100件のLLM質問を流さない。モデルを呼ばないdeterministic microbenchと、最後の3 raw live canaryだけにする。
  • 性能改善を理由に検証前のpush/restartをしない。pushはユーザーの明示指示がある場合のみ。

前提・仮定

  • 現在の5,535 stable pagesに対して IndexStore とcanonical enumerationの差が0である。実装直前に再確認し、差が1件でもあれば作業を止めて原因を解消する。
  • 全ページparity確認はbootstrap/recoveryの責務とし、以後のChronovisor管理下writeは変更対象を特定できるreceiptを必ず残す。receiptを出さないwriterが見つかった場合は、そのwriterだけ既存mutation APIへ寄せてからhot pathを切り替える。
  • 手動編集・Git checkoutなどChronovisor管理外の変更はingest前景で毎回探索しない。既存のfilesystem change signalがあれば対象pathを差分反映し、対象を特定できないoverflow/障害だけdirty markerからbackground full reconcileする。新しい常駐watcherはこのPlanでは作らない。
  • foreground semantic routeはMPS、incremental routeはCPUで、別backend instanceとして構成されている。MPS document encodeは既存self-testで実行済み。
  • 125B generation終了後にstrict publicationへ入るため、通常はgeneration用accelerator activityと重ならない。実機gateでは125Bをresidentのまま確認する。
  • semantic deltaの形式、dimensions、source hash、generation identityは変えないため、data migrationは不要。
  • 最短解を優先し、Phase 1–3で目標を満たしたら後続の追加最適化は実装しない。

ベンチマーク契約

LLM品質比較ではなく、ホスト処理を再現する3ケースだけを使う。wall-clock assertionはCIに入れず、CIでは呼出し回数と判断parityを固定する。

ケース狙いモデル呼出し
A: 新規create・既存一致なし最悪の存在確認、全候補score、semantic fallback、dedupeを通す。microbench 0回 / live 1回
B: create提案だがsame/near titleありcreate→update変換、同一target衝突、score/reason/result parityを通す。microbench 0回 / live 1回
C: 既存update + 17KB/14 semantic documentscasefold/Unicode/loose/alias、対象entry 1件のupsert、strict publish、read-backを通す。microbench 0回 / live 1回

semantic候補matrixは warm-up 1回後に各3回だけ測る: 現行CPU batch 1、CPU batch 4/8/16、既存MPS document route。ANEは既存実行可能routeが発見された場合だけ同じmatrixへ加え、変換やdownloadはしない。

実行手順

  1. 0. 実行前freeze: git status、running services、125B runtime identity、IndexStore 5,535件parity、background semantic jobs、memory/swapをread-onlyで記録する。process起動時のfull reconcileを1回実測し、全writer/callerの refresh() とmutation receiptを棚卸しする。保護中dirty差分をmanifestへ明記する。
  2. 1. Red-capable feedback loop: scripts/benchmark-ingest-hot-path を最小1ファイルで作り、A–Cをmodel callなしで再現する。baselineとしてtarget resolution、catalog、all_pages/_scan_disk/full refresh/targeted upsertの各回数、semantic publish、artifact→next triggerをJSON保存し、現状の遅さを再現する。
  3. 2. bootstrap snapshot化: process起動時だけfull reconcileしてstoreをreadyにする。ingest_triage.py のfolder/countを IndexStore へ置換し、_find_page_casefold()/_find_page_resilient() を同じインメモリpage id集合から解決する。canonical path検証とalias/曖昧contractは維持する。
  4. 3. 同一解決のmemoize: validator 1回の中で同じoperationのeffective targetをdictで1回だけ解決する。まずここまでを測り、target-resolution gateを満たせばglobal cacheや候補indexは作らない。
  5. 4. receipt差分反映: 既存のcreated/updated receiptとprepared pathから、変更entryだけを同じmutation境界で IndexStore へupsertする。changed_pages=[] は0件、1ページ変更は1件、Nページ変更はunique N件とし、full refreshは常に0回。同じ更新済みsnapshotをread-backへ渡し、差分反映失敗はdirty + recoveryとしてfail closedにする。
  6. 5. semantic matrix: 125B resident状態でCPU batch 1/4/8/16とMPS document routeを比較し、速度、cosine parity、query競合、RSS、swap、lease timeoutを記録する。選定ルールを満たした1案だけを実装する。
  7. 6. strict fast lane実装: MPSがgate合格なら index_pages(wait=True) のみ _embed_foreground_documents() へ通し、wait=False workerはCPUのままにする。不合格なら既存 incremental_max_batch の実測最速値だけを採用する。
  8. 7. 可視化: 既存runtime status / console eventへ4つのhost phaseとmonotonic elapsed msを追加する。Decision Traceの線・node・6パターン表示には触れない。
  9. 8. 行動parityと回帰テスト: exact、casefold、NFC/NFD、loose、alias、ambiguous、reserved system、same-title、near-title、missing update、no-op、strict read-back、MPS failure fallbackをred→greenで確認する。bootstrap後は all_pages()、_scan_disk()、full refresh() を例外化してA–Cが完走すること、create/update、複数page、idempotent replay、差分反映失敗→recovery、外部dirty→background reconcileを固定する。
  10. 9. 全体quality gate: focused pytest、semantic tests、全pytest、ruff、mypy、import-linterを実行する。debug instrumentationとthrowaway artifactを除去する。
  11. 10. 実機acceptance: A–Cのlive rawを各1回だけ通す。trace/API/runtime log/semantic generation/read-back/dashboard stageを同じjob idで照合し、下記すべての閾値を満たす。
  12. 11. scoped commit: scan/refresh最適化とsemantic fast laneを分離commitし、保護中dirty差分を含めない。pushはユーザーが明示した時だけ行い、GitHub-backed runtimeではpush後にrestart、archive commit、health、live checkの順を守る。
  13. 12. receipt: baseline/candidate/final JSON、テスト出力、runtime identity、memory/swap、file SHA256、commitをevidence manifestへ固定し、このPlanを done にする。

Rollback

  • data schemaとsemantic delta形式を変えないため、rollback migrationは不要。page本体が正本なので、IndexStore差分が不完全でもfull reconcileで再構築できる。
  • semantic gateに失敗した場合はfast-lane commitだけをrevertし、同期CPU経路へ戻す。targeted applyに失敗した場合はそのcommitだけをrevertして従来refreshへ戻し、full reconcile後にA–C parityを確認する。
  • read-back miss、cosine < 0.999、query regression > 10%、125B tok/s regression > 5%、memory/swap超過、lease timeout発生のいずれかで即rollback。
  • GitHub-backed productionでrollbackする場合も push → restart → archive commit → health → live check の順を守る。
  • rollback後にA–Cを再実行し、旧correctnessとruntime identityの回復をreceipt化する。

受け渡しメモ（次担当へ）

  • 最初に触るべきroot causeは src/chronovisor/ingest/ingest.py の _find_page_casefold() / _find_page_resilient() と、src/chronovisor/ingest/ingest_triage.py の2つの all_pages()。CSSやoMLX tuningから始めない。
  • _existing_candidate_metas() は既に IndexStore を使っている。新しい候補cacheを作る前に、shared page finderを直し、同一validator内の重複解決だけをdictで止める。
  • IndexStore.refresh() は変更本文だけをparseするが、_scan_disk() で全ページをstatする。変更後に1回へまとめる案も最終形ではない。起動時baselineの後は、apply_prepared_operations() が既に返すcreated/updatedとprepared pathを差分receiptとして使う。
  • 最初のtargeted applyは既存entry builderとin-memory derived rebuildを再利用する。そこで閾値を満たす限り、差分backlink engine、journal、別DBは作らない。永続cache flushが残余遅延になった場合だけ、page本体から起動時再構築できる性質を使ってhot path外flushを追加検討する。
  • strict semanticの候補は src/chronovisor/search/semantic_service.py の既存 _embed_foreground_documents()。新providerは不要。
  • read-backの正しさは速度より優先。非同期化ではなく、同期処理そのものを短縮する。
  • Phase 1–3で閾値を達成したら、job coalescing、複数raw並列化、normalized candidate global indexは実装しない。実測で残余が閾値を超えた時だけ次Planに分離する。
