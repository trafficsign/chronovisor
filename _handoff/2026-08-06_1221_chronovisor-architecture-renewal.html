Plan: Chronovisor 全体アーキテクチャ刷新（Campaign O–V）

running plan_xxx 1970-01-01T00:00:00+09:00

目的

  • Chronovisor 全体を、既存の機能別フォルダ分けから、依存方向・runtime所有権・永続化契約まで強制できるアーキテクチャへ段階的に移行する。
  • UserPromptSubmit の Recall、Stop の lossless save、background convergence、exceptional repair の4経路を、外部挙動と安全境界を維持したまま明確な use case／port／adapter に分離する。
  • Dashboard/Cortex を含む観測面も同じ原則で分割し、リアルタイム性・視覚品質・イベントの意味を落とさず、変更箇所を局所化する。
  • 過去 Campaign A–N の成果を土台にし、再配置済みモジュールや廃止済みshimを作り直さない。今回の中心は、その後に増えた循環依存と責務集中を閉じることに置く。
完了時の要約: production package 間の多重SCCをゼロにし、productionからlabへの依存をゼロにし、runtime artifactごとのwriter／lock／schema ownerを一意にする。全品質ゲート、隔離全pytest、GitHub-backed本番のlive確認まで通す。

やってはいけないこと（必須）

  • 一括rename・一括移動・全層同時切替のbig-bang refactorをしない。各Campaignは単独でgreen・rollback可能にする。
  • 外部API、51 console script名、durable worker module名、CLI引数、MCP schema、HTTP/SSE/WebSocket payloadを、明示的なversioned migrationなしに変えない。
  • ~/.chronovisorのpath、保存byte列、cursor、receipt、queue順序、artifact identity、authority hash、lock/CAS/fsync/rollback順序を「内部整理」として暗黙変更しない。
  • runtime/を再生成可能なcacheとして一括削除・移動しない。projectionと、durable queue・authority artifact・receipt・identity registryをowner registryで区別する。
  • ingest、background jobs、semantic SQLite lease、page mutation、decision authority、Ollama、accelerator、sleep/convergenceのlockを一つの汎用lockへ統合しない。
  • Recallのdeadline・fail-open、mutation/authorityのfail-closed、model budget、single-flight、idempotencyを弱めない。
  • 大型関数capの引き上げ、lint除外、mypy ignore、テスト削除、goldenの無条件更新で見かけ上greenにしない。
  • 同名・類似helperを、timezone、invalid-row handling、locking、fsync、byte format、例外方針の一致を証明せず統合しない。
  • 静的zero-inboundだけでmoduleやscriptを削除しない。entry point、python -m、LaunchAgent、durable job string、docs、runtime archiveを照合する。
  • 本番~/.chronovisorをpytestのrootに使わない。隔離rootと持続的JUnitを必須にする。
  • Cortexのノード数・光量・動き・イベント頻度を落として性能を作らない。UI redesignや新機能をrefactor commitへ混ぜない。
  • 既存の未追跡_handoff/2026-06-11_0042_recall-redesign.mdとlogs/を編集・stage・削除しない。
  • local checkoutだけを本番扱いしない。push済みcommit、runtime archive、running process、health、live behaviorが一致するまで完了にしない。

実行手順

  1. Campaign O — Green baselineと不変条件の固定
    • 専用branchを作り、HEAD、worktree、package/import graph、hotspot、51 entry points、7 tracked plist、authority/schema hash、production healthをmachine-readable baseline artifactへ記録する。
    • 現在のRuff・mypy・large-function policy failureを、先にcharacterization testを足してから修正する。cap引上げや対象除外は禁止。
    • knowledge_graphをdomain inventoryとcore forbidden listへ追加し、現存edge/SCCを出力するarchitecture fitness scriptを追加する。
    • 隔離rootで全pytestをJUnit付き実行し、失敗・flaky・外部service依存を分類する。CIにはまず現行コマンドとartifact保存をそのまま載せる。
    • Recall/Save/Ingest/repair、Dashboard/Cortexについてgolden payload、durable bytes、latency/frame/memoryの変更前基準を採取する。
    Exit: 既存挙動のまま全baseline gateがgreen。以降の各Campaignが同一基準で比較可能。
  2. Campaign P — Contracts、ownership、依存fitness — in progress (P0)
    • ADRで上記layer、許可依存、public API、compatibility期間を確定する。package名の変更自体を目的にしない。
    • durable artifact／queue／lock／socket／schema／workerごとに、単一writer、reader、lock scope、version、retention、recovery ownerをregistry化する。
    • 本番classification/decisionが参照するlab utility・adoption schema/validatorをproduction contractへ移し、production→labをImport Linterで禁止する。
    • 新規cross-domain edge禁止を先に有効化し、既存edgeは期限・owner・除去Campaign付きledgerでのみ許可する。例外の増加をCIで拒否する。
    • private symbolのcross-domain importと、schema manifestが実装定数をimport収集する構造を、明示registry/contractへ反転する。
    Exit: production→labがゼロ。新しい循環edgeは追加不能。すべてのruntime stateにownerがある。
  3. Campaign Q — RuntimeContextとdurable infrastructure
    • RuntimeContext/RuntimeLayoutと、clock・filesystem・lock・process・model・socketのportを定義し、composition rootで実装を注入する。
    • import時に固定されるCHRONOVISOR_ROOTや派生pathをcompatibility adapterの背後へ置き、小さいvertical sliceから明示contextへ移す。
    • atomic write、sealed JSON、append-only JSONL、directory fsync、file lock、CASを共通durable primitivesへ集約する。ただしbyte formatと順序が一致するvariantだけを統合する。
    • 共通化するのはprimitiveであり、各ownerのlock lifetime、lease、retry、tombstone、ACK protocolは統合しない。MCP process-local jobとdurable background queue、JSON queueとSQLite semantic queueを別contractとして保持する。
    • core.ollamaをtransport、resource lease/residency、calibration、activity telemetryへ責務分離し、callerには狭いclient/lease portだけを公開する。
    • schema migrationはdual-read/single-write、crash recovery、旧artifact replay、rollback testを備え、live readerがゼロになるまで旧readerを消さない。
    • 最初のproduction pilotはread-onlyなDashboard snapshot queryにし、次にHook/MCP adapterへ広げる。authority mutation pathをpilotにしない。
    Exit: 移行済みuse caseをtemporary root/fake clock/fake clientで起動でき、production bytes/hash/lock順序がbaselineと一致。
  4. Campaign R — 4つのruntime loopをvertical sliceで再構成
    • R1 Capture/Stop: host parser、lossless delta、receipt、audit enqueueをtyped use caseへ分離。Stopの即時returnとbyte-exact性を守る。
    • R2 Recall/UserPromptSubmit: evidence gate、search/graph、processor、Field、publicationを一つのdeadline-aware application serviceへ整理し、各段をport化。最終BM25 fallbackとfail-openを保持する。
    • R3 Ingest/convergence: prepare/review/apply/read-backを明示state machineへし、transaction owner、authority check、lease、CAS、rollback、terminal stateを型で表す。巨大compatibility facadeは薄い委譲だけにする。
    • R4 Exceptional repair: routine uncertaintyとfrontier code repairをpackage境界でも分離し、incident evidence/budget/24h guardだけがrepair adapterへ到達できるようにする。
    • 各sliceはcharacterization → 新実装shadow/adapter → byte/payload比較 → canary →旧経路retireの順で独立commit・独立rollbackする。
    • service protocol変更はserverのadditive reader/fieldを先にdeployし、health確認後にclientを切替える。queueはexpand → drain → contract、authority/schema変更は最後に行う。
    Exit: 4 loopのorchestrator、domain policy、I/O adapterが分離し、各use caseに直接テスト可能な入口が一つある。
  5. Campaign S — Package cycle closureとouter layerの縮小
    • decision↔ops、recall↔search、decision↔ingest、ingest↔ops等を、Campaign Rで得たports/eventsへ置換し、SCCを一辺ずつ縮める。
    • hosts.serverからraw atomic publish、search/read、status assembly、ingest triggerの実装をuse caseへ移し、MCP serialization adapterへ縮小する。
    • ops内のdomain mutationを各domain application serviceへ戻し、opsはscheduling/composition/observabilityだけにする。
    • script・python -m・durable module string・LaunchAgent参照を全数追跡し、compatibility wrapper経由でcanonical targetへ移す。
    Exit: production top-level package graphに複数node SCCがなく、Import Linterのlayer contractが全てgreen。
  6. Campaign T — Dashboard/Cortexとentrypoint surface
    • Dashboard backendをsnapshot query/materializer、Cortex event stream、auth、HTTP/SSE/WebSocket transport、static servingへ分割する。observerからdomain mutationを起こさない。
    • app.jsをAPI client・normalized store・panel rendererへ、cortex.jsをscene state・layout/simulation・event effects・renderer・controlsへ分割し、明示module APIにする。
    • Cortexは単一requestAnimationFrame scheduler、bounded queue/object pool、visibility pause、cold/live refresh分離を維持し、Nodeで実行できるbehavior testへ文字列assertionを置換する。
    • 51 console script名はcompatibility wrapperとして維持しつつ、共通launcher/command registryへ集約する。obsolete候補はruntime参照監査後だけ削除する。
    • 既存viewportでDOM寸法・重なり・stream freshnessを実測し、60秒steady stateとRecall/Save連打でframe pacing、event-to-visual latency、memory slopeがbaseline以下であることを確認する。
    Exit: 表示・操作・リアルタイム性を維持し、backend/frontend各責務が独立テスト可能。51 entry pointsは全てcallable。
  7. Campaign U — 品質面の全面引き上げ
    • strict mypyをcore/contractsからapplication/domainへpackage単位で拡張し、broad ignoreなしで完了させる。
    • pytestをunit/contract/integration/liveのmarkerへ分類し、authority・durability・recovery・deadline pathのbranch coverage baselineと低下禁止を導入する。
    • architecture graph、large-function policy、public API、entrypoint、launchd、schema/hash、forward/reverse importsを単一verification commandとCI artifactへ統合する。
    • 重複helperとdead-code候補をownership registryに照らして処理し、統合しないvariantには差異をtest/docで残す。
    • 巨大関数はlock/transaction境界を壊さず、pure projection・validation・effect adapterから分ける。すべてpolicyに個別rationaleとcapを持たせる。
    Exit: local/CIの同一gateがgreenで、architecture・型・durability契約が新規変更を自動拒否できる。
  8. Campaign V — Compatibility retirement、最終監査、本番切替
    • 旧adapter/schema/module pathごとにlive利用ゼロ、queue drain済み、migration/replay成功、rollback可能を証明してから削除する。
    • architecture docs、runtime ownership registry、operator runbook、failure/rollback手順、Campaign O–V完了記録を更新する。
    • 隔離全pytestのJUnit、全static/architecture gate、51 entry points、全tracked plist、authority/schema hash、golden bytes/payload、Cortex perfを最終確認する。
    • 意図したfileだけcommitし、push後に影響LaunchAgentだけ再起動する。runtime archiveのdirect_url.json commit、PID、health、Recall/Save/Ingest/Cortex live smokeを照合する。
    • 異常時は直前のpush済みcommitへ戻し、同じserviceを再起動してruntime reader互換とhealthを確認する。
    Exit: GitHub、本番archive、running process、health、live behaviorが同じ完成commitを指し、旧互換層が証拠に基づいて閉鎖済み。
