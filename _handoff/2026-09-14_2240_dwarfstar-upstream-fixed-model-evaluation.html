Plan: DwarfStar正式版・モデル固定評価

done plan_6d58cceb2f794b4abe525e00e202bb46 2026-09-14T22:40:29+09:00

結論

モデルを変えず正式版に更新すると、生成速度は約7%低下した。一方、checkpoint保存と会話履歴の再利用には改善を確認した。今回の試験では正式版を本番採用せず、現行runtime・モデル・設定へ復帰した。

速度低下は6つの対応比較すべてで再現し、出力の違いや計測中のswap増加では説明されない。原因は未特定であり、最新版全体・他のMac・別モデルの速度へ一般化しない。

目的

既存QwenモデルとPLE、起動引数を固定し、DwarfStar正式マージ版 f06d3eb と現行 ffd85d4 の速度・出力・保存復元を隔離比較する。

やってはいけないこと（必須）

モデル・設定・本番バイナリの差替え、稼働中Ingestの強制終了、未依頼の本番採用は行わない。

前提・仮定

M4 Max、128 GiB。既存IQ2XXSImatrix-MXFP4Down-MTPとQ4_1 PLE、ctx262144、prefill chunk1024、MTP exact、temperature0、seed42を固定。候補は取得済みの本家マージSHAに固定。

実行手順

  1. 正式版のビルドと比較条件・復帰方法を検証。
  2. 安全境界とleaseを取得し、現行・新版・新版・現行で速度を比較。初回は既存32問とnative4件も確認。
  3. 新版の公式checkpoint・保存復元テストを既存モデルで実行。
  4. 現行サービス・モデル・設定を復帰確認し、集計・後片付けを完了して結果を保存。

実行中更新ルール

  • 実行手順のチェックは、各手順の完了直後に更新する（まとめて更新しない）。
  • チェックを更新したら、同時に 実行ログ へ時刻付きで追記する。
  • 中断時は 状態（plan-meta の JSON および .badge の data-state）を blocked にし、理由を ブロッカー に記入する。

保存・復元と会話履歴の再利用

本家の同一Pythonテストを、実行するserverの選択だけ変えて両版へ適用した。モデル・PLEは同一、版ごとにcache dirを分離。公式試験条件はctx16384、prefill chunk1024、MTP exact、KV disk cache512 MiB。通常の速度比較条件ctx262144とは別試験である。

新版は3ケース×3ターン、計4回のserver起動を含む9ターンと後段ログ検証を通過。旧版はtool-lessの3ターンを通過したが、tools-omitの2ターン目（全体5ターン目）でcached_tokens>3000の条件に失敗した。残り4ターンは未実施。

クライアントが履歴へ思考部分を戻さないツール付き会話では、旧版が入力を再計算し、新版は前の履歴を再利用した。これはこのケースの応答改善であり、全リクエストの高速化ではない。保持された思考履歴が異なり入力・出力token数も完全同一ではないため、この時間比を純粋な演算速度比として扱わない。

旧版ログには途中checkpointの session has no valid checkpoint to stage に伴う保存失敗が9件、新版では0件。旧版も回答は正しく、クラッシュではなく保存・再利用条件の失敗だった。

本番の起動設定ではKV disk cacheは有効にしていない。今回の結果だけで現行Chronovisorの全経路にこの改善が効くとは主張しない。C側のcheckpoint/snapshot/exact-resample試験は正式版で成功したが、旧版には同じCテストが無く直接対照は未実施。

復帰確認

2回の試験とも protected_unchanged=true、services_restored=true、errors=[]。現行runtime commit、binary SHA256、config.toml、DwarfStar plist、起動引数、model/PLEのsize・mtime・inodeが不変。82GBの重み全体の再hashは行わず、同じ既存ファイルを両版が読み込んだ。

復帰後の現行serverでREADY生成に成功。semantic/rerankerは新しいstatusでready=true・プロセス生存・last_error空、Ingestはidle・pending_raws=0・authority/runtime available。Dashboard HTTP200、管理対象11サービスがenabled。

完了条件

速度は対応する入力ごとに比較し、順序別と全体の変化率を報告する。3%を超える同方向の低下は今回の性能懸念として扱い、境界付近は不確実と記す。新規の出力失敗、swap増加、復帰失敗を隠さない。試験結果にかかわらず本番は現行へ戻す。

初回の生成低下を受け、正式版の既定設定を前後の対照としてGPU argmax無効・swap restore無効を各一変数で追加比較する。また、同一の公式server replay試験を旧版と正式版へ適用し、保存復元の差を確認する。追加試験も本番へ採用せず復帰する。

検証手順

prefillと生成を分離。cold行cached_tokens=0、入力ハッシュ・token数・生成本文・finish_reasonを照合。OS swapとRSSを記録。旧設定・plist・model metadata・binary SHA256とservice状態を前後比較し、復帰後にREADY生成を確認。
