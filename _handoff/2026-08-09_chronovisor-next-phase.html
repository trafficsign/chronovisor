Campaign W — 共通 LLM Runtime と Provider 互換化

動機: Chronovisor の同じコアと公開 workflow を、local-only / cloud-only / hybrid の各構成で利用できる共通 runtime に接続する。Ollama 経路を OpenAI に置き換えたり二重実装したりするのではなく、既存のローカル最適化を保ったまま、cloud provider も同じ正規化 contract に参加できるようにする。local-only を唯一の production-supported 構成とし、cloud-only / hybrid は experimental / best-effort とする。

現状

  • ollama.py facade と ollama_transport.py は分離済みで、Ollama native API を使う既存経路がある
  • ingest / decision / recall / lint / search が共有できる provider-neutral な runtime contract と、role 単位の provider / model 選択は未整備
  • retry / timeout / budget / telemetry / structured output / token usage / error の扱いが、provider をまたぐ共通実行規約になっていない

設計原則

ingest / decision / recall / lint / search
              │ role + capability
              ▼
      shared LLM runtime contract
          ├─ Ollama native driver
          └─ OpenAI-compatible driver

application 側は provider 名で分岐せず、role と必要な capability を runtime に要求する。provider 固有機能は driver の optional capability として隔離し、共通ワークフローの意味論を変えない。

role に設定した provider / model が失敗しても、別 provider へ暗黙に fallback しない。provider 間の fallback / escalation は、将来導入する場合も明示 policy としてのみ定義する。

ステップ

  1. W1: 共通 runtime contract — 既存の Ollama facade / transport の上位に、chat / generate / embedding / structured output を正規化する単一 contract を追加する。各 application workflow は provider ではなく role / capability を指定して呼び出す。
  2. W2: 共通実行規約 — retry / timeout / budget / telemetry / structured output / token usage / error normalization を runtime に集約し、どの driver でも同じ成功・失敗・観測の形式を返す。role に設定された provider / model の失敗時はその失敗を返し、別 provider へ暗黙に fallback しない。
  3. W3: adapter の並存 — Ollama native driver は /api/generate、/api/chat、/api/embed を使い、calibration / lease / model residency / unload などのローカル固有能力を optional capability として保持する。OpenAI-compatible driver は /v1/chat/completions、/v1/embeddings 等を同じ contract に正規化する。SDK 採用は adapter 内部の実装選択であり、既存 transport の強制置換とはしない。
  4. W4: provider / role profile 設定 — 正本である ~/.chronovisor/config.toml の既存 schema を provider / model profile で最小限拡張する。default provider / model と role 単位 override を組み合わせ、local-only / cloud-only / hybrid をすべて第一級の設定として表現できるようにする。embedding / semantic / rerank 等、各 role の必須 capability が設定先 provider / model で満たされることを起動時に検証する。
  5. W5: 段階移行と公開 workflow — 既存 Ollama 経路を維持しながら ingest / decision / recall / lint / search を共通 runtime に接続し、各構成の example config と support boundary を文書化する。cloud-only / hybrid は local-only と同品質という未検証の feature parity を保証せず、同じ公開 workflow と正規化 contract を提供する experimental / best-effort 実装として扱う。BM25-only fallback を残す場合は明示的な degraded mode とし、provider 障害時の暗黙 fallback には使わない。
  6. W6: 障害の正規化と可視化 — provider 失敗を共通エラーへ正規化し、Dashboard に role、設定済み provider / model、category（401 / 429 / 5xx / timeout 等）、last failure time、retry count、request ID（取得できる場合）を表示する。API key と prompt 本文は Dashboard、ログ、telemetry のいずれにも表示・記録しない。
  7. W7: validation と support boundary — full 実機 E2E と品質 eval は local-only だけを必須とする。cloud-only / hybrid の必須検証は、ネットワーク、API key、課金を不要にした offline fake HTTP adapter contract test と routing test とし、最低限 chat success、structured JSON、finish_reason / usage 欠落、401 / 429 / 5xx / timeout、embedding の順序・件数、role routing、capability validation、no silent fallback を網羅する。必要な workflow には fake runtime による smoke test を追加する。実 OpenAI 等への live smoke は credential-gated の任意 manual / release check とし、Campaign W の完了条件には含めないため、ユーザーに必須の API 費用は発生しない。
Exit Criteria: application workflow に provider 分岐がなく、すべて同じ runtime contract を経由すること。default provider / model と role 単位 override により local-only / cloud-only / hybrid を設定でき、起動時 capability validation と no silent fallback が成立すること。唯一の production-supported 構成である local-only は既存 Ollama native 経路の回帰、full 実機 E2E、品質 eval が green であること。experimental / best-effort の cloud-only / hybrid は、同じ公開 workflow と正規化 contract を提供し、offline fake HTTP adapter contract test、routing test、必要な fake runtime workflow smoke が green であること。provider 障害の共通エラーと安全な Dashboard 表示が検証され、API key と prompt 本文を表示・記録しないこと。credential-gated の実 provider live smoke と cloud / local の未検証な feature parity は完了条件に含めないこと。

研究知見: Filesystem-Based Memory for LLM Agents

論文: arXiv 2607.26637v1 — Filesystem-Based Memory for LLM Agents (2026-07)

論文の概要

ファイルシステムをLLMエージェントのメモリストアとして形式化し、3つのエージェント役割（management/search/execution）で運用する枠組み。会話メモリと手続きスキルの2設定で、5つのRQに答える大規模実験。ベンチマーク: LoCoMo, PersonaMem (32k/128k), REALTALK, ALFWorld。モデル: gpt-5.4-nano〜gpt-5.4。

Chronovisor に直接関係する知見

知見論文の根拠Chronovisor への影響
Reorganizer はデフォルトで LOSSY condense 版は REALTALK で correctness がほぼ半減（41.2 vs 77.6）。preserve 版で回復。ただし小ストア（PersonaMem 32k）では condense が優位 ingest の Ollama プロンプトに fact 保存ルールを追加すべき
Search agent の強さが回答品質に直結 management の強さは構造スタイルを買うが品質に直接効かない。search の強さは単調に寄与（nano→mini→gpt-5.4 で 62→71→83） management=Ollama（弱）、search=Claude（強）の構成は理にかなう。search チェーンの品質改善が最もアウトカムに効く
BM25 キーワード検索の併用が効く Shell ツールセット（bash + BM25）が mini management で最高成績 82.9% semantic search + keyword 一致パスの併用
ツールセットがストアの形を決める 同じモデル・指示でもツールを変えると構造が桁違いに変わる MCP ツール設計変更時は Wiki 構造への副作用を意識する
Taxonomy 準拠は最強モデル以外で侵食される schema 準拠は全モデルで時間経過とともに劣化。gpt-5.4 のみがほぼ維持 chronovisor_check を ingest のたびに回すのが理想
Curated store は元を取る Curated がデプロイコスト最安（$4.3 vs Episode log $9.0） raw→pages パイプラインの方向性は正しい。キュレーション投資はランニングコストで回収
蓄積は弱いエージェントほど価値がある No store → 蓄積ありの改善幅は弱い実行エージェントで +7.1、強いほうで +1.4 初回セッションの onboarding 品質がメモリの ROI を決める
初期メモリは生き残る chain 終了時点で gpt-5.4 curator でも 63% が edited-in-place、17% が untouched 初期ページの品質が長期的に重要。初期 ingest の品質管理を厚くする

アクション候補（優先順）

  1. ingest プロンプトに preserve ルール追加 — 最小コストで最大インパクト
  2. chronovisor_search に keyword 検索パス追加 — semantic + BM25 併用
  3. ingest 後に自動 lint 実行 — chronovisor_check をパイプラインに組み込む
  4. ツール設計の構造影響を文書化 — MCP ツール変更が Wiki 構造にどう影響するか ADR に記録
注意: 論文は「構造の精緻さ自体は回答品質を買わない」ことも示している。整理しすぎへの過剰投資は避ける。

OKF（Open Knowledge Format）互換性

参照: LLM Wikiパターンの標準化 OKF — Google Cloud が2026年6月に発表した LLM Wiki の標準仕様。

OKF は「Markdown + YAML フロントマター」で知識を構造化し、ファイル間リンクで知識グラフを形成する仕様。Chronovisor の pages/ と構造が一致する。

OKF の要素Chronovisor の対応差分
Markdown + YAML フロントマターpages/ の .md + メタデータフロントマター形式を OKF 互換に調整
ファイル間 Markdown リンク → 知識グラフ[[wikilink]] でページ間接続互換（記法の差異のみ）
アトミックノート1トピック1ページ互換
type フィールド（必須）ページ種別ありフィールド名を type に統一

OKF が「足りない」と指摘する3点と Chronovisor の対応

  1. 語彙の未統一 — Chronovisor は schema.md で独自語彙を定義済み。OKF 語彙が標準化されたら追従
  2. LLM の生成品質 — Semantic Projection で対処中
  3. 更新の仕組みがない — ingest パイプラインで解決済み。OKF エコシステムの中での差別化ポイント

アクション

  • pages/ のフロントマターを OKF 互換形式に調整。コスト極小（フィールド名のリネーム程度）
  • 対応タイミングは Campaign W と同時期、または独立した小タスクとして
