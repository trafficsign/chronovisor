概要

Campaign O–V（アーキテクチャ刷新）の完了を前提に、次フェーズとして取り組む事項をまとめる。Campaign W の共通 LLM Runtime、Campaign X の OKF v0.2 canonical migration、OSS 公開準備、研究知見の反映を含む。

O–V 計画は _handoff/2026-08-06_1221_chronovisor-architecture-renewal.html を参照。

Campaign W — 共通 LLM Runtime と Provider 互換化

動機: Chronovisor の同じコアと公開 workflow を、local-only / cloud-only / hybrid の各構成で利用できる共通 runtime に接続する。Ollama 経路を OpenAI に置き換えたり二重実装したりするのではなく、既存のローカル最適化を保ったまま、cloud provider も同じ正規化 contract に参加できるようにする。local-only を唯一の production-supported 構成とし、cloud-only / hybrid は experimental / best-effort とする。

現状

  • ollama.py facade と ollama_transport.py は分離済みで、Ollama native API を使う既存経路がある
  • ingest / decision / recall / lint / search に加え、classification、Librarian、Nemotron semantic 経路、既存 reranker を含む全 production model inference が共有できる provider-neutral な runtime contract と、共通 role mapping による provider / model 選択は未整備
  • retry / timeout / budget / telemetry / structured output / token usage / error の扱いが、provider をまたぐ共通実行規約になっていない

設計原則

all production model consumers
ingest / decision / recall / lint / search / classification
Librarian / Nemotron semantic / existing reranker
              │ role + capability only
              ▼
         LLMRuntime facade
              │ role mapping + routing + validation
              ▼
      small backend contracts
          ├─ GenerationBackend
          ├─ EmbeddingBackend
          ├─ RerankBackend
          └─ LocalRuntimeControl (optional, local roles only)

adapter families compose and register supported components
          ├─ Ollama: shared transport → Generation / Embedding / LocalRuntimeControl
          ├─ OpenAI-compatible: shared client + profile → Generation [ + Embedding / Rerank when supported ]
          ├─ Anthropic Messages: Generation
          └─ Local Transformers: Rerank

全 production model inference の入口は1つの LLMRuntime facade とするが、内部を全機能必須の巨大 interface にはしない。各 domain service は provider / model を直接選ばず、role と必要 capability だけを渡す。facade は ~/.chronovisor/config.toml の共通 role mapping から、各 role について local または API の provider / model を1つ解決し、小さな backend contract の composition へ委譲する。role ごとの割当を組み合わせて system 全体の local-only / cloud-only / hybrid 構成を作る。

domain service 自体は残す。Nemotron semantic service の常駐 / index / cache / micro-batch / job 管理と、Librarian / classification の queue / 候補生成 / isolated worker / stage cache / consensus / authority は各 domain が所有する一方、generation / embedding / rerank の model access は必ず LLMRuntime を通す。

application 側は provider 名で分岐しない。provider ブランドごとの subclass / 継承ツリーは作らず、OpenAI-compatible 経路の差分は base URL / auth / model / capabilities / parameter・response quirks を持つ小さな provider profile データに閉じ込める。互換層で吸収できない実需要が確認された時だけ protocol-specific adapter を追加する。

profile / adapter が capability truth の正本となる。structured JSON、streaming、tools（採用 workflow で必要な場合）、usage accounting は GenerationBackend が必要に応じて宣言する capability とし、初期から個別 interface を乱造しない。EmbeddingBackend は vector 生成と順序 / 件数 / 次元を、初期 contract に含める小さな RerankBackend は query / candidates と順位 / score を検証する。既存 local Transformers reranker は RerankBackend の内側へ移し、remote rerank は対応 profile と実装がある場合だけ登録する。不足 capability は従来どおり fail-closed とし、Generation / Embedding / Rerank を巨大 interface に統合しない。Ollama 固有の lease / residency / unload 等は optional な LocalRuntimeControl に隔離し、local role だけに適用する。

legacy_ollama / nemotron_service の切替は恒久的な provider 境界にしない。移行完了時には provider / model selection としての legacy switch、domain 内の直接 core.ollama.chat / core.ollama.embed、直接 Transformers inference を除去する。service / process topology の選択が必要な場合は、provider 設定から分離した execution mode として扱う。

DecisionRouter core は provider-neutral とする。local model と API model は同じ decision input、vote normalization、schema / contract validation、quorum、veto を通り、mutation authority に provider 種別による差を設けない。routing、capability、cloud egress policy を満たして role に設定された model は、provider 固有の身元証明、digest / system_fingerprint、事前の正式 adoption 評価、定期再認証 / expiry、credentialed paid live benchmark を利用開始条件にせず、直ちに合議へ参加できる。

Decision response は実行時に共通 vote 形式へ正規化し、schema / contract に失敗した vote は invalid とする。invalid vote を別 provider の応答で埋めずに合議から除外し、残る valid votes で既存 quorum / veto 条件を満たさない場合に mutation を hold して、Dashboard へ内容を開示しない安全な error を返す。形式的に valid でも判断品質が低いリスクは provider 固有 gate ではなく、既存の multi-model quorum / veto で扱う。local digest、returned model、system_fingerprint、request ID 等は取得できる場合だけ任意の audit / telemetry metadata として記録し、欠落だけを理由に cloud model を排除しない。

role に設定した provider / model が失敗しても、別 provider へ暗黙に fallback しない。provider 間の fallback / escalation は、将来導入する場合も明示 policy としてのみ定義する。

cloud data egress は provider routing / capability validation とは独立した fail-closed policy とする。既定では raw/、system/、sensitivity=high の page を cloud backend へ送信せず、通常 sensitivity の page と必要最小限の derived snippet だけを cloud-eligible とする。この制限の緩和は role と data class の両方に scope した明示 opt-in だけで許可する。policy が拒否した request は outbound call を一切行わず、別 provider へ暗黙に reroute しない。

API credential は model routing から分離した trust boundary とする。ProviderProfile が保持できるのは CredentialRef だけで、CredentialResolver は参照を opaque な SecretValue として解決し、raw secret を wire authorization に変換できるのは AuthenticatedTransport だけとする。domain service、LLMRuntime、backend、Dashboard、child process には raw secret を渡さない。security module は概念上 credential_ref、credential_resolver、secret_value、endpoint_policy、redaction に分ける。SecretValue は opaque で repr を常に redacted とし、通常の str / JSON serialization と general-purpose reveal API を持たせない。Python process memory の完全な zeroization は保証せず、perfect secret handling ではなく credible な v1 boundary として scope する。

application-owned の plaintext credential store は作らない。desktop default は allowlist した OS-native credential store（macOS Keychain、Windows Credential Locker、Linux Secret Service または KWallet）とし、明示 ref は oskeyring:openai/default、env:OPENAI_API_KEY、mounted-file:/run/secrets/openai_api_key のように表す。env: / mounted-file: は headless / CI 用の明示経路に限り、相互または keyring への自動 fallback をしない。native keyring backend は allowlist し、null / plaintext / unknown backend と keyrings.alt 等の insecure backend を拒否する。store が locked / unavailable、ref が missing、backend が rejected の場合は network I/O より前に fail-closed とする。mounted file は外部 secret mount に限定し、absolute regular file であることを検証して symlink、unsafe owner / mode、過大 size、repository 内または home 配下の plaintext store を拒否する。

config schema は raw api_key / token / authorization、URL 埋め込み credential 等を拒否する。credential CLI は credentials set / status / delete だけとし、set は TTY の hidden input を使い、secret の CLI argument と取得用 get を提供しない。credential は profile ID、exact canonical HTTPS origin、auth scheme の組へ bind する。remote endpoint は HTTPS 必須、HTTP は loopback local かつ cloud secret を使わない場合だけ許可し、TLS verification の無効化は設定不能とする。redirect は follow せず、cross-origin redirect または endpoint origin の変更には明示 rebind を要求する。Authorization を URL / query / error に含めない。

structured logging は safe-field allowlist とし、secret を log、error、Dashboard、telemetry、migration receipt、child environment のいずれにも出さない。credential resolution と provider routing は missing / locked / backend rejected / origin mismatch を理由に別 credential や provider へ fallback しない。Dashboard はこれらの安全な category と remediation hint だけを表示し、secret の値、長さ、prefix / suffix を表示しない。

ステップ

  1. W1: facade と backend contract — 既存の Ollama facade / transport の上位に、全 production model consumer が使う単一の LLMRuntime facade を追加する。内部の初期 contract は通常生成を担う GenerationBackend、vector 生成と順序 / 件数 / 次元検証を担う EmbeddingBackend、query / candidates の順位と score を検証する小さな RerankBackend、Ollama のローカル制御だけを担う optional な LocalRuntimeControl に分ける。Generation / Embedding / Rerank は独立して設定・解決し、LocalRuntimeControl は application から隠蔽して local role だけに適用する。
  2. W2: 共通実行規約 — retry / timeout / budget / telemetry / structured output / token usage / error normalization を runtime に集約し、どの adapter でも同じ成功・失敗・観測の形式を返す。request の source data classification を serialization と network I/O より前に付与し、egress policy が拒否した場合は outbound call を 0 件のまま共通エラーを返す。role に設定された provider / model の失敗時はその失敗を返し、別 provider へ暗黙に fallback しない。
  3. W3: adapter / backend composition — adapter 族は必ず1 class ずつという意味ではない。Ollama native adapter 族は /api/generate、/api/chat、/api/embed 用の共通 transport を共有し、GenerationBackend / EmbeddingBackend / LocalRuntimeControl component を構成して runtime へ登録する。OpenAI-compatible adapter 族は共通 transport / client と profile データを共有し、対応する Generation component と、profile / implementation が対応する場合だけ Embedding / Rerank component を構成・登録して各 response を正規化する。Anthropic Messages adapter 族は Generation component だけを登録し、Claude の正式経路とする。既存 local Transformers reranker は direct inference を廃止して RerankBackend 実装の内側へ移す。unsupported method を stub / NotImplemented で巨大 class に強制せず、不足 contract / capability は routing / validation で fail-closed とする。SDK 採用は adapter 内部の実装選択であり、既存 transport の強制置換とはしない。
  4. W4: provider profile、credential ref、共通 role mapping、generic endpoint — 正本である ~/.chronovisor/config.toml の既存 schema を provider / model profile と共通 role mapping で最小限拡張する。ProviderProfile は CredentialRef と origin / auth binding だけを持ち、raw credential field と URL 埋め込み credential を schema validation で拒否する。OS-native store と明示的な headless / CI ref、backend / mounted-file validation、credentials set/status/delete だけを持つ secret 非取得 CLI を security module 境界の内側に実装する。各 consumer は role + capability だけを渡し、runtime が mapping から各 role の local または API の provider / model を1つ解決する。例として search.semantic、search.rerank、librarian.review、classification.primary / classification.challenger / classification.tie_break と、必要なら classification.embedding を定義し、role ごとの単一割当を組み合わせて system 全体の local-only / cloud-only / hybrid を構成する。profile は subclass ではなく設定データとし、Qwen / Kimi / DeepSeek 等も同じ OpenAI-compatible adapter 族の共通 transport / client に別 profile を渡して扱う。初期 curated profile は OpenAI、Alibaba Qwen / DashScope、Google Gemini、DeepSeek、Moonshot / Kimi、Z.AI / GLM、Mistral、OpenRouter とする。xAI / Grok（Chat compatibility の範囲）、Groq、Together AI、Fireworks AI、Cerebras、NVIDIA NIM 等は generic OpenAI-compatible endpoint から接続できるようにし、検証済みの差分が必要になったものだけ curated profile へ昇格する。Meta Llama 等の model family は Ollama または選択した host / gateway 経由で扱い、model family 専用 adapter は作らない。
  5. W5: provider-neutral decision routing と capability validation — 共通 role mapping は各 role を単一の local または API provider / model へ解決し、その role 別割当の組合せで system 全体の local-only / cloud-only / hybrid を表現する。domain service には provider / model selection を持たせない。profile / adapter の capability 宣言を検証し、role に必要な機能がなければ起動時または実行前に fail-closed とする一方、設定済み model に provider identity / adoption gate を追加しない。DecisionRouter は local / API の全 vote に同じ入力、正規化、schema validation、quorum / veto、mutation authority を適用する。backend capability / routing の判定とは独立して role × data class の cloud egress policy を enforcement し、拒否時は別 backend を選び直さない。generation と embeddings を同じ credential で提供できる OpenAI / Qwen / Gemini / Mistral 等には cloud-only の一鍵 example を用意する。Claude / DeepSeek / Kimi / GLM 等は、対象とする公式機能で embeddings を利用できない、または確認できない場合に local embedding または別 embedding provider が必要となることを example / support docs に明記する。
  6. W6: 全 consumer の段階移行と公開 workflow — production model consumer inventory を作成し、ingest / decision / recall / lint / search、classification、Librarian、Nemotron semantic 経路、既存 reranker の generation / embedding / rerank をすべて共通 runtime に接続する。domain 固有の service / queue / cache / consensus / authority / job 管理は維持しつつ、provider / model selection と model access は runtime に限定する。移行完了時に provider / model selection としての legacy_ollama / nemotron_service switch、domain 内の直接 core.ollama.chat / core.ollama.embed、直接 Transformers inference を除去し、必要な service / process topology は provider 設定から分離した execution mode として扱う。現行の Ollama 固有 adoption / authority 拘束は provider-neutral な decision execution contract へ置換または縮小する。remote-only role は Ollama daemon / lease / residency / unload と local Transformers model に触れず、hybrid でも optional な LocalRuntimeControl は local role だけに適用する。各構成の example config と support boundary、cloud egress の既定拒否 data class、cloud-eligible な範囲、role × data class に scope した明示 opt-in の設定境界を文書化する。cloud-only / hybrid は local-only と同品質という未検証の feature parity を保証せず、同じ公開 workflow と正規化 contract を提供する experimental / best-effort 実装として扱う。BM25-only fallback を残す場合は明示的な degraded mode とし、provider 障害、vote invalid、egress 拒否時の暗黙 fallback には使わない。

Campaign X — OKF v0.2 Canonical Migration

Decision: OSS 公開前に pages/ を OKF v0.2-compatible Chronovisor superset の内部 canonical bundle へ一括移行する。最終 live layout は ~/.chronovisor/raw/、~/.chronovisor/pages/、~/.chronovisor/system/、~/.chronovisor/runtime/ を直接使う clean layout とし、conversion 自体は LLM を必須としない決定論的な one-shot migration とする。長期 dual-read / dual-write や generation / symlink 経由の indirection は採用しない。

公式参照: Open Knowledge Format specification、Google Cloud: OKF v0.2。実装対象は現行の v0.2 とするが、正式標準化または凍結済みとは扱わない。

設計原則

  • Chronovisor OSS はソフトウェア本体を配布し、各ユーザーの私有知識はローカルの pages/ に蓄積する。OKF は初期リリースで interchange / sync product を作るためではなく、知識を proprietary format に閉じ込めない on-disk canonical / portability boundary として採用する。
  • ~/.chronovisor/raw/ は不変の原本として相対 path、size、SHA-256、全 bytes を移行開始から cleanup 完了まで変更しない。~/.chronovisor/pages/ は OKF-compatible bundle、~/.chronovisor/system/ は private canonical namespace として、それぞれ同じ full-YAML parser / serializer と standard Markdown link extraction / resolution を使う共通 canonical document syntax へ同時に移行する。一方、system/ は固定 filename / page ID、特権 access / semantics、startup loading、既定の cloud egress 拒否を維持し、portable な pages/ OKF bundle とその conformance / import / export の対象には含めない。
  • 運用イベントの正本は ~/.chronovisor/runtime/activity.jsonl とし、pages/log.md は canonical pages から再生成可能な OKF reserved change history とする。reserved な index.md / log.md は concept / page / UID / KG の対象として数えず、index / change-history 専用入力として扱う。
  • page lifecycle は OKF 標準の status: draft/stable/deprecated だけを canonical とする。draft は通常運用前、stable は通常検索 / 更新の対象、deprecated は通常運用外とし、default search、link-expanded search、mutation、retention candidate selection は stable だけを対象にする。draft / deprecated は exact lookup または明示指定でだけ扱う。page lifecycle と registry state は namespace を分離し、registry の処理状態を page status に encode しない。
  • 旧形式を読めるのは offline の migration executable だけとする。cutover 後の production runtime は新 canonical だけを read / write し、旧新混在や長期 dual-read / dual-write を許さない。
  • rollback は migration run 中だけの一時機構とし、runtime/migrations/<run-id>/rollback-backup/ から pages/ / system/ を同じ rollback scope で journaled coordinated restore する。rollback と re-cutover の演習後は backup、staging、journal、sentinel、live root の旧 Markdown を削除し、legacy directory / bridge symlink / canonical/ / generations/ / current symlink を最終 layout に残さない。既存 Git history は書き換えないが、production runtime や rollback の source としては扱わない。
  • Chronovisor 独自 field は、廃止する lifecycle / archive 専用 field を除き OKF extension として意味を保ち、その他の unknown field も保持する。nested YAML を正しく parse / serialize し、unknown key / value の意味を semantic round-trip で保持できる正式な YAML parser / serializer を採用し、正規表現や ad hoc parser を canonical 経路に残さない。

  7. X7: portability / conformance — repository 内で version 固定した conformance validator により pages/ をその場で検証し、pages/ 自体を portable bundle として filesystem-native に copy / backup / restore する手順を文書化する。初期リリースでは専用 import / export CLI と external bundle の merge / sync / update / overwrite workflow、interchange 用 conversion engine を作らず、実需が確認されるまで延期して Campaign X の完了条件に含めない。
