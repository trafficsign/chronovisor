Campaign W — 共通 LLM Runtime と Provider 互換化

動機: Chronovisor の同じコアと公開 workflow を、local-only / cloud-only / hybrid の各構成で利用できる共通 runtime に接続する。Ollama 経路を OpenAI に置き換えたり二重実装したりするのではなく、既存のローカル最適化を保ったまま、cloud provider も同じ正規化 contract に参加できるようにする。local-only を唯一の production-supported 構成とし、cloud-only / hybrid は experimental / best-effort とする。

現状

  • ollama.py facade と ollama_transport.py は分離済みで、Ollama native API を使う既存経路がある
  • ingest / decision / recall / lint / search が共有できる provider-neutral な runtime contract と、role 単位の provider / model 選択は未整備
  • retry / timeout / budget / telemetry / structured output / token usage / error の扱いが、provider をまたぐ共通実行規約になっていない

設計原則

ingest / decision / recall / lint / search
              │ role + capability
              ▼
         LLMRuntime facade
              │ routing + validation
              ▼
      small backend contracts
          ├─ GenerationBackend
          ├─ EmbeddingBackend
          └─ LocalRuntimeControl (optional)

adapter families compose and register supported components
          ├─ Ollama: shared transport → Generation / Embedding / LocalRuntimeControl
          ├─ OpenAI-compatible: shared client + profile → Generation [ + Embedding when supported ]
          └─ Anthropic Messages: Generation

application 側の入口は1つの LLMRuntime facade とするが、内部を全機能必須の巨大 interface にはしない。facade は role / capability を解決し、小さな backend contract の composition へ委譲する。

application 側は provider 名で分岐しない。provider ブランドごとの subclass / 継承ツリーは作らず、OpenAI-compatible 経路の差分は base URL / auth / model / capabilities / parameter・response quirks を持つ小さな provider profile データに閉じ込める。互換層で吸収できない実需要が確認された時だけ protocol-specific adapter を追加する。

profile / adapter が capability truth の正本となる。structured JSON、streaming、tools（採用 workflow で必要な場合）、usage accounting は GenerationBackend が必要に応じて宣言する capability とし、初期から個別 interface を乱造しない。EmbeddingBackend は vector 生成と順序 / 件数 / 次元を検証し、Ollama 固有の lease / residency / unload 等は optional な LocalRuntimeControl に隔離する。rerank 等は実需要が発生した時だけ別 contract を追加する。

role に設定した provider / model が失敗しても、別 provider へ暗黙に fallback しない。provider 間の fallback / escalation は、将来導入する場合も明示 policy としてのみ定義する。

cloud data egress は provider routing / capability validation とは独立した fail-closed policy とする。既定では raw/、system/、sensitivity=high の page を cloud backend へ送信せず、通常 sensitivity の page と必要最小限の derived snippet だけを cloud-eligible とする。この制限の緩和は role と data class の両方に scope した明示 opt-in だけで許可する。policy が拒否した request は outbound call を一切行わず、別 provider へ暗黙に reroute しない。

ステップ

  1. W1: facade と backend contract — 既存の Ollama facade / transport の上位に、application が使う単一の LLMRuntime facade を追加する。内部の初期 contract は通常生成を担う GenerationBackend、vector 生成と順序 / 件数 / 次元検証を担う EmbeddingBackend、Ollama のローカル制御だけを担う optional な LocalRuntimeControl に分ける。generation role と embedding routing は独立して設定・解決し、LocalRuntimeControl は原則 application から隠蔽する。
  2. W2: 共通実行規約 — retry / timeout / budget / telemetry / structured output / token usage / error normalization を runtime に集約し、どの adapter でも同じ成功・失敗・観測の形式を返す。request の source data classification を serialization と network I/O より前に付与し、egress policy が拒否した場合は outbound call を 0 件のまま共通エラーを返す。role に設定された provider / model の失敗時はその失敗を返し、別 provider へ暗黙に fallback しない。
  3. W3: 3 adapter 族の composition — adapter 族は必ず1 class ずつという意味ではない。Ollama native adapter 族は /api/generate、/api/chat、/api/embed 用の共通 transport を共有し、GenerationBackend / EmbeddingBackend / LocalRuntimeControl component を構成して runtime へ登録する。OpenAI-compatible adapter 族は共通 transport / client と profile データを共有し、対応する Generation component と、profile が embeddings 対応の場合だけ Embedding component を構成・登録して Chat Completions / Embeddings を正規化する。Anthropic Messages adapter 族は Generation component だけを登録し、Claude の正式経路とする。unsupported method を stub / NotImplemented で巨大 class に強制せず、不足 contract / capability は routing / validation で fail-closed とする。SDK 採用は adapter 内部の実装選択であり、既存 transport の強制置換とはしない。
  4. W4: provider profile と generic endpoint — 正本である ~/.chronovisor/config.toml の既存 schema を provider / model profile で最小限拡張する。profile は subclass ではなく設定データとし、Qwen / Kimi / DeepSeek 等も同じ OpenAI-compatible adapter 族の共通 transport / client に別 profile を渡して扱う。初期 curated profile は OpenAI、Alibaba Qwen / DashScope、Google Gemini、DeepSeek、Moonshot / Kimi、Z.AI / GLM、Mistral、OpenRouter とする。xAI / Grok（Chat compatibility の範囲）、Groq、Together AI、Fireworks AI、Cerebras、NVIDIA NIM 等は generic OpenAI-compatible endpoint から接続できるようにし、検証済みの差分が必要になったものだけ curated profile へ昇格する。Meta Llama 等の model family は Ollama または選択した host / gateway 経由で扱い、model family 専用 adapter は作らない。
  5. W5: capability validation と embedding routing — default provider / model と role 単位 override を組み合わせ、local-only / cloud-only / hybrid を表現する。profile / adapter の capability 宣言を検証し、role に必要な機能がなければ起動時または実行前に fail-closed とする。backend capability / routing の判定とは独立して role × data class の cloud egress policy を enforcement し、拒否時は別 backend を選び直さない。generation と embeddings を同じ credential で提供できる OpenAI / Qwen / Gemini / Mistral 等には cloud-only の一鍵 example を用意する。Claude / DeepSeek / Kimi / GLM 等は、対象とする公式機能で embeddings を利用できない、または確認できない場合に local embedding または別 embedding provider が必要となることを example / support docs に明記する。
  6. W6: 段階移行と公開 workflow — 既存 Ollama 経路を維持しながら ingest / decision / recall / lint / search を共通 runtime に接続し、各構成の example config と support boundary を文書化する。cloud egress の既定拒否 data class、cloud-eligible な範囲、role × data class に scope した明示 opt-in の設定境界も support docs に明記する。cloud-only / hybrid は local-only と同品質という未検証の feature parity を保証せず、同じ公開 workflow と正規化 contract を提供する experimental / best-effort 実装として扱う。BM25-only fallback を残す場合は明示的な degraded mode とし、provider 障害時または egress 拒否時の暗黙 fallback には使わない。
  7. W7: 障害の正規化と可視化 — provider 失敗と cloud egress 拒否を共通エラーへ正規化し、Dashboard に role、設定済み provider / model、category（401 / 429 / 5xx / timeout / cloud egress denied 等）、last failure time、retry count、request ID（取得できる場合）を表示する。egress 拒否は内容を開示しない安全な文言で示し、credential、prompt、content は Dashboard、ログ、telemetry のいずれにも表示・記録しない。
  8. W8: validation と support boundary — full 実機 E2E と品質 eval は local-only だけを必須とする。cloud-only / hybrid はネットワーク、API key、課金を不要にした offline fake HTTP adapter contract test と routing test を必須とし、出荷する全 curated profile の offline fixture、config parsing、capability validation を追加する。generic endpoint は共通 contract fixture で検証し、最低限 chat success、structured JSON、finish_reason / usage 欠落、401 / 429 / 5xx / timeout、embedding の順序・件数、generation / embedding の独立 routing、adapter 族が対応 component だけを構成・登録すること、unsupported capability の fail-closed、no silent fallback を網羅する。cloud egress の offline test では、既定で raw/ / system/ / sensitivity=high を拒否すること、通常 sensitivity の page から作る必要最小限の derived snippet は許可できること、role × data class に scope した明示 opt-in だけが制限を緩和すること、拒否時の outbound request が 0 件で別 provider への silent fallback もないことを検証する。必要な workflow には fake runtime による smoke test を追加する。全外部 provider の live 試験は完了条件にせず、実 provider live smoke は credential-gated の任意 manual / release check とするため、ユーザーに必須の API 費用は発生しない。
Exit Criteria: application からは単一の LLMRuntime facade を使い、内部は GenerationBackend / EmbeddingBackend の小さな contract と optional な LocalRuntimeControl を composition すること。Ollama native、OpenAI-compatible、Anthropic Messages の3 adapter 族が共通 transport / client を必要な component 間で共有し、対応 component だけを構成して runtime へ登録すること。巨大 interface や unsupported stub、provider ブランド subclass / 分岐を作らず、Ollama 固有の local control を application から隔離すること。初期 curated profiles と generic OpenAI-compatible endpoint が利用でき、ブランド差分を小さな profile データに閉じ込めること。default provider / model と role 単位 override により local-only / cloud-only / hybrid を設定でき、generation から独立した embedding routing、capability truth に基づく起動時または実行前の fail-closed、no silent fallback が成立すること。source data classification が serialization / network I/O より前に付与され、provider routing / capability とは独立した role × data class の cloud egress policy により、既定で raw/ / system/ / sensitivity=high が拒否されること。通常 sensitivity の page と必要最小限の derived snippet だけが cloud-eligible で、制限緩和は scope された明示 opt-in に限られ、拒否時は outbound request 0 件かつ別 provider への reroute がないこと。唯一の production-supported 構成である local-only は既存 Ollama native 経路の回帰、full 実機 E2E、品質 eval が green であること。experimental / best-effort の cloud-only / hybrid は、出荷する curated profile の offline fixture / config parsing / capability validation、generic endpoint の共通 contract fixture、routing test、cloud egress policy test、必要な fake runtime workflow smoke が green であること。provider 障害と egress 拒否の共通エラー、安全で内容非開示の Dashboard 表示が検証され、credential、prompt、content を表示・記録しないこと。cloud egress の support / config boundary が文書化されていること。全外部 provider の live 試験、credential-gated の実 provider live smoke、cloud / local の未検証な feature parity は完了条件に含めないこと。

Campaign X — OKF v0.2 Canonical Migration

Decision: OSS 公開前に pages/ を OKF v0.2-compatible Chronovisor superset の内部 canonical bundle へ一括移行する。runtime / index 全体にまたがる変更だが、conversion 自体は LLM を必須としない決定論的な one-shot migration とし、長期 dual-read / dual-write は採用しない。

公式参照: Open Knowledge Format specification、Google Cloud: OKF v0.2。実装対象は現行の v0.2 とするが、正式標準化または凍結済みとは扱わない。

設計原則

  • Chronovisor OSS はソフトウェア本体を配布し、各ユーザーの私有知識はローカルの pages/ に蓄積する。OKF は初期リリースで interchange / sync product を作るためではなく、知識を proprietary format に閉じ込めない on-disk canonical / portability boundary として採用する。
  • raw/ は不変の原本として1 byte も変更しない。pages/ と system/ は同じ full-YAML parser / serializer と standard Markdown link extraction / resolution を使う共通 canonical document syntax へ同時に移行する。一方、system/ は固定 filename / page ID、特権 access / semantics、startup loading、既定の cloud egress 拒否を維持する private namespace であり、portable な pages/ OKF bundle とその conformance / import / export の対象には含めない。
  • 旧形式を読めるのは offline の migration executable だけとする。cutover 後の production runtime は新 canonical だけを read / write し、旧新混在や長期 dual-read / dual-write を許さない。
  • rollback は旧形式の併存ではなく、cutover 前の一貫 snapshot から pages/ / system/ を同じ rollback scope として、X1 で固定した物理 root と swap / restore primitive により coordinated restore する。Chronovisor 独自 field は OKF extension として意味を保ち、unknown field も保持する。
  • nested YAML を正しく parse / serialize し、unknown key / value の意味を semantic round-trip で保持できる正式な YAML parser / serializer を採用し、正規表現や ad hoc parser を canonical 経路に残さない。

Deterministic mapping

現行要素OKF v0.2 canonical mapping不変条件
type 欠落機械的に Concept を設定任意の精緻化は cutover 後の別作業
summaryOKF description へ移し、runtime / index も description を canonical とする内容を要約し直さない
status: active/deprecated/archived意味衝突を避けて chronovisor_status extension へ移す。OKF status: draft/stable/deprecated は正確に写像できる時だけ設定根拠のない OKF status を捏造しない
updated、uid、tags、raw_keywords、entities、recall_questions、classification*、sensitivity 等必要な Chronovisor extension として保持unknown field を落とさず、generated / verified / sources を根拠なく生成しない
[[target]]、[[target|label]]、[[target#section]]registry / path 解決により bundle-relative な standard Markdown link へ決定論的に変換code / frontmatter 内は変更せず、broken link を明示記録し、移行で新規 broken を作らない
root / subdir の index.md と log.mdOKF reserved 形式へ再生成し、root index に okf_version: "0.2" を設定派生 index として canonical pages から再現可能にする

ステップ

  1. X1: mapping / invariants の固定 — 実装開始前に、pages/ / system/ の物理 root と coordinated cutover / rollback に使う swap / restore primitive を選定・文書化する。その上で両 namespace の field、path、link、reserved / fixed file、extension、schema / version 境界と、前後比較する不変条件を fixture と仕様に固定する。OKF v0.2 spec §11 準拠の conformance validator / fixtures は portable な pages/ bundle 用として repository 内で version 固定し、system/ は対象外であることも固定する。
  2. X2: 新 runtime 対応 — pages/ と system/ の両方を、正式な full-YAML parser / serializer と standard Markdown link extraction / resolution を共有する1つの canonical document stack に対応させる。prompt / writer、search / recall / lint / backlink / UID / KG は共通 syntax と link graph を扱いつつ、両 namespace の異なる schema / privilege semantics を維持する。cutover 後にいずれかの旧形式を読む production parser / reader は残さない。
  3. X3: idempotent migration tool — pages/ と system/ を同じ coordinated cutover scope に含めた dry-run manifest と、namespace を分離した staging output を生成し、old→new の hash / path / link mapping を記録する。canonical serialization は frontmatter に限り、body bytes は standard Markdown link syntax への変換以外で変更せず、LLM を必須経路に置かない。
  4. X4: offline cutover preflight — writers / services を停止して jobs を drain し、pages/、system/、index、state、decision preimage / artifact 等の一貫 snapshot と raw/ 全 hash を記録する。staging で両 namespace の parse / semantic round-trip / link resolution、system/ の固定 identity と privilege boundary、portable pages/ bundle への混入がないことを検証する。
  5. X5: coordinated cutover / rebuild — staging migration を全検証後、X1 で固定・文書化した物理 root と swap / restore primitive に従い、pages/ と system/ を1つの coordinated cutover scope として切り替える。両 namespace を対象に lexical / semantic / link / backlink / UID / KG 等の index と combined link graph をすべて再構築する。page bytes / frontmatter hash に依存する decision review / CAS / preimage / artifact は旧値を再利用せず、無効化して正規手順で再生成する。
  6. X6: production restart / live verification — production を新 canonical document stack だけで再起動し、health、主要 workflow、pages/ の live read / write、system/ の startup init loading、search / recall / link graph visibility と privilege boundary、mixed-state 不在を確認する。
  7. X7: portability / conformance — repository 内で version 固定した conformance validator により pages/ をその場で検証し、pages/ 自体を portable bundle として filesystem-native に copy / backup / restore する手順を文書化する。初期リリースでは専用 import / export CLI と external bundle の merge / sync / update / overwrite workflow、interchange 用 conversion engine を作らず、実需が確認されるまで延期して Campaign X の完了条件に含めない。
  8. X8: optional LLM enrichment — type / description 等の精緻化は cutover 後の別作業とし、migration の完了条件に含めない。
Exit Criteria: pages/ は前後で page 数、UID 集合、解決済み edge 集合が一致し、system/ は全 fixed filename / page ID が維持されること。両 namespace で frontmatter の semantic content を維持しつつ canonical serialization を許容し、body bytes は standard Markdown link syntax への変換以外で不変であること。両 namespace で新規 broken link が 0、対象 frontmatter が full YAML parser で parse / semantic round-trip 可能であり、共通 document stack と combined link / index behavior が検証されること。pages/ の全 concept の type が non-empty で、Campaign X で実装または採用して repository 内で version 固定した OKF v0.2 spec §11 conformance validation が portable な pages/ bundle に対して green であること。pages/ が変換なしでそのまま portable bundle として validation を通り、filesystem-native な copy / backup / restore 手順が文書化され、system/ document が1件もその bundle や OKF conformance 対象に含まれないこと。専用 import / export CLI と external bundle の merge / sync / update / overwrite workflow は初期リリースおよび Campaign X の完了条件に含めないこと。pages/ / system/ の migration 2回目の diff が 0 で、raw/ の全 bytes / hash が不変であること。production に旧形式の parser / reader が残らず、全 index 再構築後の search / recall / ingest / lint / decision、system/ の startup init loading と search / recall / link graph visibility、固定 identity / privileged access / semantics / default cloud-egress denial、必要な local production live smoke が green であること。mixed canonical state がなく、X1 で固定・文書化した物理 root と swap / restore primitive により、同じ rollback scope の一貫 snapshot から coordinated rollback を演習・検証済みであること。schema / version 境界を持ち、OKF 後続 version は明示 migration として扱い、v0.2 への無期限固定も暗黙追従もしないこと。

研究知見: Filesystem-Based Memory for LLM Agents

論文: arXiv 2607.26637v1 — Filesystem-Based Memory for LLM Agents (2026-07)

論文の概要

ファイルシステムをLLMエージェントのメモリストアとして形式化し、3つのエージェント役割（management/search/execution）で運用する枠組み。会話メモリと手続きスキルの2設定で、5つのRQに答える大規模実験。ベンチマーク: LoCoMo, PersonaMem (32k/128k), REALTALK, ALFWorld。モデル: gpt-5.4-nano〜gpt-5.4。

Chronovisor に直接関係する知見

知見論文の根拠Chronovisor への影響
Reorganizer はデフォルトで LOSSY condense 版は REALTALK で correctness がほぼ半減（41.2 vs 77.6）。preserve 版で回復。ただし小ストア（PersonaMem 32k）では condense が優位 ingest の Ollama プロンプトに fact 保存ルールを追加すべき
Search agent の強さが回答品質に直結 management の強さは構造スタイルを買うが品質に直接効かない。search の強さは単調に寄与（nano→mini→gpt-5.4 で 62→71→83） management=Ollama（弱）、search=Claude（強）の構成は理にかなう。search チェーンの品質改善が最もアウトカムに効く
BM25 キーワード検索の併用が効く Shell ツールセット（bash + BM25）が mini management で最高成績 82.9% semantic search + keyword 一致パスの併用
ツールセットがストアの形を決める 同じモデル・指示でもツールを変えると構造が桁違いに変わる MCP ツール設計変更時は Wiki 構造への副作用を意識する
Taxonomy 準拠は最強モデル以外で侵食される schema 準拠は全モデルで時間経過とともに劣化。gpt-5.4 のみがほぼ維持 chronovisor_check を ingest のたびに回すのが理想
Curated store は元を取る Curated がデプロイコスト最安（$4.3 vs Episode log $9.0） raw→pages パイプラインの方向性は正しい。キュレーション投資はランニングコストで回収
蓄積は弱いエージェントほど価値がある No store → 蓄積ありの改善幅は弱い実行エージェントで +7.1、強いほうで +1.4 初回セッションの onboarding 品質がメモリの ROI を決める
初期メモリは生き残る chain 終了時点で gpt-5.4 curator でも 63% が edited-in-place、17% が untouched 初期ページの品質が長期的に重要。初期 ingest の品質管理を厚くする
