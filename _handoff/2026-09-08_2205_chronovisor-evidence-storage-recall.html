保存契約と最小の変更

Rawと既存の原資料を保持し、そこから再構築できる証拠projectionを検索する。既存Wikiの手動編集や独立した原資料も保全する。全ページの内容がRawだけから再生成できるとは仮定しない。今回、Raw / pages / systemの全面変換や新しい正本データベースへの移し替えは行わない。

層契約実装上の判断
原文・原資料source UID、版/digest、話者、元の言語、取得時刻、該当範囲。原文は発言・観測の証拠であり、内容の真偽を自動認定しない。既存RawStore / receipts / page identityを使う。直接編集されたpageは、その版の出典として扱う。
証拠レコード安定したrecord ID、source参照と範囲、原文抜粋、検索用の文脈、対象・scope、種類、時刻、有効性、明示された訂正関係。EvidenceAtom / EvidencePacketと既存projectionを拡張。最初は既存chunkを保持し、その後に会話の出来事・話題、文書節へ単位を改善する。
派生索引・表示BM25 / ANN / 想定質問 / 要約 / 必要な関連リンクはrecordとsourceの版へ結び付ける。消失・陳腐化時に再構築可能。既存のSQLite・ANN・publication lock / generation契約を使う。独立fact候補や索引を無制限に増やさない。Wikiは閲覧・互換経路を保持する。

P2実装時の具体化:Raw由来は既存EvidenceAtom / EvidencePacketの契約を維持する。pageだけが原資料の資料は、canonical page版とbyte範囲を持つpage-evidence-projection.v1として既存ResearchStoreへ保存する。Raw receipt・発言者・事実の有効期間を捏造してEvidencePacketへ昇格させない。隔離したsection-v1索引の結果はSourcePassageまで復元する。テストでP1のContextItemと既存context rendererへの受け渡しを検証し、本番Cの接続はP3まで有効化しない。research→recallの新依存を追加せず、既存architecture制約を保つ。新しい正本DBは追加しない。文脈・検索キーはembedding入力のみで、それぞれ512文字を上限とし、原文引用には含めない。

必須フィールドの意味

  • 識別・出典:既存UID、source digest、receipt digest、範囲の単位を再利用する。Rawのlogical byte rangeとMarkdownの文字位置・chunk ordinalを混同せず、source種別ごとに明示して原文との一致を検証する。doc IDやordinalだけを版をまたいだidentityとして扱わない。record revisionはsource UID・digest・source固有の範囲・kind・固定projection版に結び付け、同一入力から同一identityを再構築する。改訂時は別revisionとして旧参照の混入を拒否する。
  • 原文と検索キー:原文抜粋と生成した検索用文脈を別fieldで保持。事実・別名・質問をキーへ加えても、生成文を原文引用に見せない。日英の原文を残し、元の言語以外の別名・訳語は補助キーとする。
  • 出来事と条件:会話は一つの判断・出来事・話題、文書は節を基本単位にする。上限を超えたら分割し前提への参照を保持。発言者、提案 / 決定 / 実行結果 / 未検証の区分、対象プロジェクトや言語などの条件を失わない。
  • 時間:出来事の時間・事実の有効期間と、システムが記録した時間を分離。不明は不明のまま、相対日付の元表現も残す。取り込み時刻を出来事の時刻として補完しない。
  • 訂正:SUPPORTS / CONTRADICTS / SUPERSEDESと元の根拠を既存契約で表す。同じsubject・scope・条件への明示的変更だけを置換として扱う。新しい発言・頻出だけで旧事実を打ち消さない。提案や反実仮想を実行結果へ昇格させない。
  • 派生物の版:source digestとextractor/model/prompt/schema versionを保存し、生成出力を証跡として固定。同じ固定出力からのprojection再構築を決定論的にする。LLMを再実行して同じ文章になることは要求しない。

同期Recallの経路

質問 → 既存BM25 + 意味検索 → record / chunk候補
     → source identity・scope・有効性を検証
     → 必要な前提・明示訂正を固定予算で補う
     → 出典付きの該当本文 → 既存のcontext compiler → 本体AI

L2は事前生成・検証済みprojectionだけを使用し、同期Raw全探索や新しい生成的query plannerを加えない。抽出遅延・失敗時は既存の許可されたpage teacher / lexical fallback、または根拠不足の応答を使う。時刻が曖昧な質問を推測した期間でhard filterしない。sourceアクセス・sensitivityを索引への複製で緩和しない。

採用gate（本計画の初期提案値。P0で既存contractのより厳しい値を継承し、候補結果を見る前に固定）

  • identity / 範囲 / sensitivity / authority違反0、生成LLMの検索時追加呼出し0、原文の欠落・改変0。既存の絶対品質lower boundがあればそのまま維持する。
  • 主指標の全根拠注入率がA比で5 percentage points以上改善し、paired 95%信頼区間の下限が0を上回ることを初期の有効性gateとする。Bが成立した場合、Cの追加採用はB比の改善と費用を別途判定し、効果が不明ならBに留める。
  • 回答正確性はpaired差の95%信頼区間下限が−2 points以上。言語sliceの点推定が各々Aを下回らず、旧情報利用・根拠なし誤注入の件数もAを上回らない。少数例の0件を真の誤り率0の証明とはしない。
  • 回答指標の実行定義（品質実行前）:回答正確性は既存の独立採点器のcorrectness（0〜1）を使い、grounding / citationとの平均にはしない。3反復の各case内paired差を算術平均し、120個のcaseを標本単位として既存paired bootstrap 2,000回で95%区間を計算する（case_id順、B対A seed 1731、C対B seed 1732）。grounding / citationも全件記録する。採点はP4で実際に注入したprivate保存contextとSHAに対して行い、検索を再実行して置換しない。正式gold review、独立したrunner / scorer identity、既存calibration gateの検証を前提とし、未校正・欠損値・実行receipt不整合は未受入とする。
  • warm p95はA以下、4秒のL2上限を拡大しない。coldの超過率・fallback・外部に返る実時間もAより悪化しない。既存の厳しいlatency gateがあれば継承する。4秒以内は「瞬時」の証明ではなく、短縮量も必ず報告する。
  • 不要な回答生成の省略:候補の主指標・出典保全・latencyの必要条件が固定holdout評価で不合格なら、その候補は不採用とし、追加の回答生成・採点を省略できる。未測定の回答正確性は未測定と記録し、合格へ読み替えない。B対AとC対Bを別々に判定し、Cの不合格をBの不合格へ転用しない。この規則は候補の結果を観測する前に登録する。
  • 120問で統計的に判定不能なら成功扱いしない。未使用実例を60問単位で追加し、同じ固定候補で最大240問まで評価する追加段階をP0で登録する。途中結果を見て都合のよい時点で停止せず、追加段階を使う場合は逐次判定の補正方法も先に固定する。上限でも不明ならCの採用を見送る。
  • 基準Aが既存の絶対品質条件を満たさない場合、相対改善だけで本番有効化しない。固定回帰ケースの欠落修正は独立して出荷判断できるが、Recall全体の精度向上を実証済みと呼ばない。

新規保存との共通化・入力の扱い

  • 新規保存と既存分の再処理で、同じrecord schema・抽出手順・validator・publication経路を使う。既存分はsnapshotを共通の変換入口へ投入するbackfillとし、移行専用の第二の保存形式を作らない。
  • 機械的に取り出せるchunk・見出し・既存出典・日時・metadataは先に回収し、既存summary / questions / entitiesを再利用。LLMは不足する文脈補完・出来事分割・条件抽出だけに使う。
  • 元の会話がある場合は、アクセスpolicyに適合する範囲でその根拠を使う。pageだけが残る場合は当該page revisionを原資料として保持し、失われた発言・日時・理由を復元したように生成しない。複数ページが同じRawを指す場合はsource単位で抽出を再利用し、参照を保つ。
  • 各ワーカーには割当済みの入力束と出力用の専用作業領域だけを渡す。秘密情報を含む作業ツリー全体や会話履歴を自動contextに載せない。元のpages / Rawと本番DB・索引をワーカーに直接変更させない。処理結果は構造化した候補recordとreceiptとして返す。

最大10並列への段階的増加

  1. 少量試行:P0の開発用資料から日英・長短・訂正・page-onlyを含む20〜40件を選び、1ワーカーでschema一致、出典一致、条件の保持、処理時間・tokens・再試行率を測る。heldoutの質問や正解は渡さない。Muse Sparkで作るCの試験結果もP4に含める。
  2. 増加:同じ品質基準で1 → 2 → 5 → 最大10ワーカーへ増やす。ワーカー数は常に設定可能とし、provider共有枠、CPU/RAM、通常ingest/Recallの待ち時間を確認する。10並列で10倍速になるとは仮定しない。
  3. 流量制御:全ワーカー合計の同時requestとtokensを単一の制御点で制限。429 / timeout / quota発生時はRetry-Afterまたはbackoffを守り、並列数を下げる。上限到達時はcheckpointから停止・再開し、アカウントや端末を増やして上限を回避しない。追加課金や別残高への自動fallbackは有効化しない。
  4. 全件実行:P4でCの採用条件を満たしてから全manifestを処理する。Bだけが採用された場合は、既存chunk索引の機械的再構築で足りる範囲に留め、不要な全件LLM再抽出を行わない。1ジョブは独立したページ/節/会話segmentの小束とし、全8,000ページを一つのpromptへ入れない。

分担・再開・更新整合性

  • 既存queue / lease / receiptを再利用する。仕事のidentityはsource UID・digest・抽出設定版に結び付ける。1ジョブは同時に1ワーカーへ割り当て、期限切れの担当は再割当可能。結果採用時は現在のlease/attemptを確認し、遅れて戻った旧ワーカーの結果を二重反映しない。単一DB writerで結果検証・merge・publicationを行う。
  • LLMへのrequest自体は再試行で重複し得るが、採用はjob identityで冪等にする。完了checkpoint、失敗理由、試行回数、source/config digest、モデル、使用tokensを保存。schema不正や出典不一致は隔離し、有限回の再試行後は未処理として残す。無限retryと未検証の自動採用をしない。
  • ワーカー間のentityや訂正関係は、固定IDと原文参照を使って検証・統合する。各ワーカーが他のワーカーの生成文を独立した新証拠として引用したり、別scopeの事実を上書きしたりしない。
  • 処理中は既存Recallを稼働させる。snapshot後の新規・更新分は共通ingest経路で追跡し、採用前にsource digestを再照合。改訂分は新revisionを再queue、削除・失効・権限変更済みのsourceは旧結果を採用しない。全量処理後の差分追いつきと短いpublication境界で整合したgenerationへ切り替える。
  • 旧page/Rawを保持し、新projection・索引を隔離領域で作る。全件検証とP5のcanary/rollback条件を満たすまで本番の参照を変えない。新projectionを無効化しても元資料と従来経路で回答できる状態を維持する。
