Plan: Chronovisor Integrity, Recall, and Operational Truth Hardening

running plan_596dfe01bc574196a8085d0b34acd25f 2026-08-23T19:44:57+09:00

目的

  • Chronovisor の現行機能を増やす前に、派生データの完全性、Recall の可用性、運用状態の真実性を同じ受入契約で固める。
  • 監査で確認した P0/P1 の欠陥を、Raw を不変に保った小さい修正単位で解消し、テスト・runtime archive・API・DOM・service state の一致まで検証する。
  • 今夜の実装順を固定する。ただし時刻では完了判定せず、各 Phase の Exit Criteria を満たした時だけ完了にする。

やってはいけないこと（必須）

  • Raw v2、quarantine、receipt、既存監査証跡を削除・上書きしない。repair は検証済み Raw からの derived-only 操作に限定する。
  • 全例外を BM25 fallback へ丸めない。既知の可用性例外だけを契約化し、入力不正・実装不良・sensitive filter 違反は隠さない。
  • 注入候補を自動で used と記録しない。実際に使用したページだけを decision/session identity と結合する。
  • DFlash の process-global lease、sensitive filter、authority preflight、promotion gate を緩めない。
  • 新しい DB、cache、framework、単一実装の抽象層を導入しない。既存の reconciler、deterministic fallback、health snapshot、JSONL writer を深くする。
  • 無関係な dirty worktree、local-only commit、別 Plan の checkbox/state/log を変更しない。本 Plan は cross-reference と receipt だけを持ち、既存 Plan の更新は各 Plan の owner に委ねる。push、restart、GitHub 設定変更は所有者の明示承認後だけ行う。
  • P2 Evidence Reconstruction を P0/P1 より先に production promotion しない。

実行手順

  1. Phase 0 — baseline と変更境界を固定する。
    • 既存 chronovisor raw command groupへread-onlyの projection-status --full --json を最小追加する。既存 projection_bundle_state_for_parent とprocessed stateを再利用し、total/valid/missing/invalid、parent raw_id/digest、manifest/child/receipt/quarantineのroot-relative path、processed membershipだけを返す。
    • uv run pytest -q tests/test_cli.py tests/test_raw_archive.py tests/test_raw_semantic_projection.py でfixtureのmissing child、invalid receipt、processed parent、path redaction、runtime file mutation 0を固定し、diagnostic-only commitにする。
    • git status、HEAD/origin、runtime archive、service PID/health、対象ログ件数を baseline.json に保存する。
    • uv run chronovisor raw projection-status --full --json の出力を projection-inventory.before.json に保存し、既存20件の全fieldを確認する。Raw archive自体は別途 uv run chronovisor raw verify --full --json で検証する。
    • 対象 source と test の index coverage を確認し、不足範囲は直接読む。既存の共通経路を特定してから変更する。
    • Exit: 修正前状態を同じコマンドで再現でき、無関係な作業がない。baseline drift があれば数値だけ更新し、対象契約を勝手に変えない。
  2. Phase 1 / P0-A — processed parent も対象にする bounded projection reconciler を実装する。
    • get_pending_raw_files の通常 ingest と分離し、processed raw_id の canonical sort を1巡する cursor を既存 .orchestrator_state.json へ additive に保存する。1 drain pass は128 parents・1 batchまで、batch 完了ごとに checkpoint し、末尾まで達した時だけ wrap する。
    • 1 batch の追加wall time p95を250ms以下に保つ。20 passes のうち3回連続で250msを超えたら reconciler をdisableして Phaseを未完了に戻し、batch size以外の新しいscheduler/cacheは作らない。
    • manifest/receipt/child の missing・digest mismatch・invalid schema を分類し、Raw v2 digest と quarantine evidence を保持する。
    • 既存の projection verification/requeue 経路を再利用し、verified Raw から deterministic reproject する。LLM ingest を再実行せず、重複 page mutation を作らない。
    • raw projection-status --full --json dry-run inventory → 1件 canary → 全20件 repair → 同じ full inventory の順に実行し、projection-repair.after.json に before/after disposition を残す。
    • Focused test: processed parent の child を欠損させると検出・修復され、Raw bytes/digest は不変、LLM call 0、再実行は idempotent。
    • Command: uv run pytest -q tests/test_orchestrator_characterization.py tests/test_failure_supervisor_characterization.py tests/test_raw_semantic_projection.py tests/test_raw_archive.py。
    • Exit: 全 manifest inventory で missing/invalid child が0。元の20件は全件 repaired。新規 duplicate、Raw mutation、quarantine deletion が0。1件でも hold が残れば Phase 1 は blocked であり完了不可。
    • Rollback: 既存 ingest config に置く1個の boolean kill-switch で reconciler を止める。feature-flag framework は作らない。derived repair の commit 単位を戻し、Raw/quarantine/receipt はそのまま残す。
  3. Phase 2 / P0-B — semantic availability failure を既存 BM25 fallback へ接続する。
    • 所有範囲は availability-exception mapping と telemetry の差分だけ。既存 Plan precision-preserving latency の commit cf354b329aeab95aad77113a144a3a486f8d761b で完成済みの direct BM25/L1 fallback、filter/render、副作用ゼロ経路を再実装・再構成しない。
    • RecallBudgetExhausted に加え、契約済みの SemanticServiceUnavailable / capacity-busy 系だけを既存 run_deterministic_fallback へ渡す。
    • failure class、reason、elapsed、deadline reserve、degraded=true、search_mode=bm25-fallback を保存する。sensitive filter と query budget は元の境界を維持する。
    • 未知の例外は error として可視化し、無条件 fallback で隠さない。
    • Focused test: uv run pytest -q tests/test_recall_runtime.py::test_semantic_service_unavailable_uses_deterministic_fallback tests/test_recall_runtime.py::test_unknown_semantic_error_is_not_fallback で known unavailable → nonempty BM25、600ms reserve内、sensitive result 0、重い subsystem call 0、正しい telemetry。unknown exception は fallback されない。
    • Implementation Exit: availability failure が空の search_mode=error へ落ちず、direct fallback契約とfocused testsがgreen。diffがexception mapping/telemetry/testsだけであることを recall-availability.focused.json に保存してcommitする。live閾値はPhase 6のdeploy後closureで判定する。
    • Rollback: availability exception mapping の commit を戻し、旧 error path へ復帰。ログ schema は後方互換のまま残す。
  4. Phase 3 / P1-C — Recall の「実際に使われた」を end-to-end で結合する。
    • host hook → search → read → used receipt → answer episode を追い、decision_id、session_id、実使用 page_ids、model/system/sampler identity の欠落点だけを直す。保存する正本は append-only exact exposure receipt。
    • 候補提示と実使用を区別し、注入・表示だけで used を生成しない。used/ignored は label、truth、student feature、authority、promotion gate に使わない。
    • offline distillation の P5/P8/P9、capture_only、active/candidate/LKG pointer は一切変更しない。将来の causal utility は同Planの exact exposure/outcome predicate を満たす別経路だけが所有する。
    • used rate、missing decision/session/page IDs、unassigned split、binding unknown、production replayable を health/report に出す。
    • Focused test: 100 decision の固定fixture（used 50 / unused 50）で used join 50/50、unused false join 0/50、orphan/duplicate 0、identity欠落0。uv run pytest -q tests/test_recall_log_schema.py tests/test_recall_answer_eval.py で固定する。
    • Implementation Exit: fixtureのsilent signal loss 0、legacyのunassigned/binding unknown不変、distillation capture-only不変を recall-signal.focused.json に保存してcommitする。live cohortはPhase 6のdeploy後closureで判定する。
    • Rollback: receipt propagation の commit を戻す。既存ログを削除せず、追加 field は reader が無視可能にする。
  5. Phase 4 / P1-D — operational truth を runtime/API/UI/CLI で統一する。
    • 正本を runtime_state、mutation_ready/authority、active_failure、last_failure、liveness age に分離する。成功時は active failure を clear し、履歴は timestamp 付きで保持する。
    • health overall が current authority failure と stale liveness を評価し、Dashboard は状態・年齢・stale/refreshing を DOM と aria-live で表示する。
    • /api/health に materialized_at、age、stale、refreshing、source generation を付ける。fast snapshot は thin summary、full details は明示要求に限定する。
    • chronovisor status --json を bounded summary にし、巨大な full details は既存の chronovisor health --json だけに残す。新しいCLI modeは増やさない。
    • oMLX は一部 endpoint 成功でも失敗 endpoint を落とさず endpoint_status/partial を返す。reranker は launchd PID/ancestor と Unix socket connect をready判定に使い、idleな observed_at ageは診断値に留める。
    • Focused test: (1) running+success+historical failure → active_failure=null/通常badge、(2) current authority blocked → mutation_ready=false/alert/BLOCKED、(3) configured TTL超過liveness → stale=true/alert/STALE、(4) mixed oMLX failure → partial=true/degraded/DEGRADED、(5) idle-but-live reranker → ready=true。JSON、CLI、DOM、aria-live の期待値を同一fixtureで固定する。
    • Command: uv run pytest -q tests/test_runtime_status.py tests/test_health.py tests/test_dashboard.py tests/test_reranker_service.py。
    • Exit: 5ケースで API、CLI、Dashboard が完全一致。status --json は64KiB以下、warm 20回のp95 <=1000ms、cold単発 <=3000ms。active failure と履歴を誤表示せず、結果を operational-truth.json に保存する。
