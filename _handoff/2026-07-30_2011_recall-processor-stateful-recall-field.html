Plan: Chronovisor Recall Processor + Stateful Recall Field

done plan_3508b0284d4542af92f176b0dd67af5a 2026-07-30T20:11:56+09:00 baseline bf790e96c486

目的

  • 現行の最高品質経路 BM25 + Nemotron 2048 → graph/fusion → BGE reranker を同期Recallへ戻し、ページ単位で関連性を証明できるcertified pointerを0〜6件、うちsupporting spanを含むrich evidenceを最大2件だけ注入する。
  • Recall Processor を正確性の境界・teacher、Stateful Recall Field をセッション常駐の候補空間・高速なワーキングメモリとして統合する。
  • 投機結果は非公開で保持し、Evidence Certificateを通った記憶だけcommitする。誤った先行注入と次ターン訂正は禁止する。
  • 既存のSynaptic Cortexを、ランダムな発火演出から、実際の刺激・伝播・残留活性・抑制・棄却・commitを観測できるデバッガへ昇格する。
  • 最高精度を基準に、常駐化・候補照合・発火フィールド・Anti-Index・Recall Compilerでレイテンシを下げる。速度のための品質劣化は採用しない。
最終判断: 発火フィールド単独をauthorityにしない。Recall Processorが正解を作り、そのcertificate・実利用・明示評価でFieldの配線を育てる。 ダッシュボード統合は付随作業ではなく、この設計の観測・評価・調整機構として完了条件に含める。

先に固定するデータ契約

1. Reranker service

  • 新規: search/reranker_service.py、search/reranker_client.py、entrypoint chronovisor-reranker-service。
  • Unix socketは~/.chronovisor/runtime/reranker.sock、socket/状態ファイルは所有者限定。query本文をログへ残さない。
  • methods: health、warm、rerank(query,page_ids)。service側でページを解決し、本文cacheをcontent hashで無効化する。
  • レスポンスはpage_idごとのraw score、rank、latency、model/revision、cache statusを保持する。現行のrank-only blendでraw scoreを捨てない。
  • bounded queue、single MPS worker、top 10 batch、client circuit breaker、remaining hook budget伝播、unavailable時の現行fused path fail-openを必須とする。

  • certificate pass + commitはsilver。実chronovisor_read/recall_usedはstrong。ユーザー明示評価またはlocked goldはgold。
  • certificate fail、未commit、ignoredは自動的な負例にしない。
  • 注入は固定件数ではなく、intent coverage、既出カードとの差分、marginal utility、token budgetで停止する。certified pointerは最大6件、その中でsupporting spanを本文表示するrich evidenceは最大2件とする。
  • pointerはtitle、relation/reason、page id、certificate idだけを短く出し、本文が必要ならホストLLMがchronovisor_readでpullする。件数上限まで無理に埋めない。

  • WebSocketは接続直後にhello + snapshot、その後ordered event batches。seq gapはsnapshot再取得で回復する。

実行手順

Phase 0 — 94件の失敗解剖と基準凍結

必須先行mutationなし ここを完了するまでproduction選択ロジックを変更しない。

  1. search-golden.jsonlのmanual集合（manual-curated 62 + auditor 22 + auditor_precision 10 = 94）をquery本文をGitへ入れず、ref/hash付きsealed manifestとして固定する。
  2. chronovisor-eval --source-filter manual --top-n 50を基準に、candidate_union → fused → reranked → page_gate → committed → host_usedのstage traceを追加する。
  3. 94件を①candidate top50漏れ、②fusion順位落ち、③BGE順位落ち、④page selector棄却、⑤commit後未利用へ排他的に分類する。
  4. Overall / Japanese / hard-94を分離し、Recall@5/10、MRR、negative-hit、pointer/rich evidence別の注入Precision、関連記憶Recall、abstention、p50/p95/max、4秒超過を保存する。
  5. 現行Auto Recallの既知不具合をfixture化する: 弱いRRF scoreの飽和、hit_count floor、過去3query混入、既出上位page除外による下位noise繰上げ。
  6. live p95 251.6msに対して250msのNemotron timeoutを再測定し、35B稼働中を含む安全なtimeout/remaining-budget境界を決める。

受入ゲート: 既知の29.6/49.3/53.5%と20.0% negative-hitを再現、または差分理由をcase単位で説明できる。stage合計とE2E結果が一致し、同じmanifestで決定的に再実行できる。

Phase 1 — BGE rerankerの常駐service化

  1. 既存semantic_service.py/semantic_client.pyのUnix socket・health・breaker設計を参照し、障害分離したreranker service/clientを追加する。
  2. 現行reranker.pyのmodel loaderとbatch scoringをservice側へ移し、page本文cacheとMPS warmupを短命Hookの外へ出す。
  3. RerankOutcomeをraw per-page score、rank、marginを保持する契約へ拡張し、同点時は元rank/page_idで決定的にする。
  4. launchd/com.trafficsign.chronovisor-reranker.plist、installer、status artifact、health CLI、resource coordinationを追加する。
  5. idle、Nemotron同時、35B稼働、memory pressure、service kill/restart、stale socketを負荷試験する。
  6. Auto Recallでは最初にshadowでbefore/after/latencyのみ記録し、注入結果は変えない。

受入ゲート: hard-94の品質がin-process BGEと一致。warm top-10 batchを含むRecall E2E p95 < 3.5s、4s超過0。service停止時は現行fused pathへfail-openし、host promptを止めない。

Phase 2 — Recall Processorとページ別Evidence Certificate

  1. recall/recall_processor.py（または同責務の小モジュール）を追加し、候補生成・rerank・page selection・certificate・commitを分離する。_run_recall_implへ再び巨大責務を戻さない。
  2. _score_normのRRF飽和とhit-count floorを廃止し、channel別raw featureと同一model revision内で較正可能なscoreへ置換する。
  3. current promptを主queryにし、過去queryを直接候補へ混ぜない。曖昧な短文だけ直前1turn/episode stateで書き換える。
  4. 既出pageを候補選択前に除外しない。最良pageを先に決め、その後に「再注入不要」「更新されたので再提示」を判定する。
  5. claims.pyのevidence_span/source_line、検索snippet、query termを使い、候補ごとにsupporting spanを選ぶ。必要ならspan chunkをBGEで再採点する。
  6. 明確なpass/rejectは決定論的に処理し、曖昧な1〜2件だけ9B judge、さらに必要な場合だけ35Bへ昇格する。
  7. certificate通過後もintent coverage、claim/entityの新規性、既出カードとの冗長性、marginal utility、token budgetで順に選び、追加価値がなくなった時点で停止する。
  8. certified pointerは最大6件、うちsupporting spanを表示するrich evidenceは最大2件、低信頼なら両方0件。全カードにcertificate idとpage idを付けるが、hostへ内部scoreや秘密情報を過剰注入しない。
  9. certificate ledgerとlabel quality（silver/strong/gold）を実装し、teacher biasを監査できるようpolicy/model/content digestを保存する。

受入ゲート: locked評価でpointer/rich evidence別の注入Precision目標90%以上、hard-94の関連記憶Recallと53.5% rerank Recall@5を非劣化、negative-hit ≤20%、pointer最大6件・rich evidence最大2件、無関係集合では0件。multi-intent fixtureでは必要な独立論点を落とさず、single-intent fixtureでは上限まで水増ししない。lower confidence boundとabstentionを併記し「0件だけでPrecisionを稼ぐ」設定を不採用にする。

Phase 3 — Stateful Recall Fieldをshadow実装

  1. graph_expand_results()内のneighbor生成・typed edge・traceを再利用可能なengineへ抽出し、現行stateless 2-hop挙動を回帰fixtureで固定する。
  2. recall/recall_field.py、recall_field_schema.py、recall_field_store.pyを追加し、session hash/topic epoch単位でsparse activationを永続化する。
  3. direct stimulus（prompt exact/entity、MCP search/read、record、certificate、commit）、typed spread、wall-clock/turn decay、global inhibition、capacity、不応期、negative activationを決定論的に実装する。
  4. wikilink/backlink/entity/tagはdegree正規化する。positive co-fireだけを学習signalにし、exposure co-fireはauthority経路から除外する。
  5. active/shadowの2 bufferとtopic epochを持ち、新entity・active centroid低一致・強いsemantic jumpでtopic reset/full-search fallbackする。
  6. shadow評価ではteacher結果をField入力へ混ぜてから一致率を測る「答え漏洩」を禁止する。teacher commitは次turn以降の学習だけに使う。
  7. ordered event log、sealed sparse snapshot、retention、session TTL、corrupt recovery、concurrent writerを実装する。

受入ゲート: shadow modeは注入を一切変更しない。固定event replayが決定的、session分離、TTL、topic reset、capacity上限、露出非学習をテスト。Field update p95 < 50ms、artifactにprompt/page本文漏洩なし。

Phase 4 — Synaptic Cortexを「本物の脳」へ接続

  1. _handoff/2026-07-29_2116_chronovisor-neural-graph-viewer_mockup.htmlをvisual正本、既存/cortexとVS Code風Activity Barをintegration正本として、別画面を増やさずStateful Recall Field debuggerへ昇格する。
  2. ops/cortex.pyはbrowser-safe projectionだけを担当し、Field engine/stateをDashboard層へ置かない。旧telemetry tailはtelemetry-fallbackと明示する。
  3. dashboard_static/cortex-field.jsへsnapshot/event reducer、seq gap、reconnect、session切替を分離し、cortex.jsを再巨大化させない。
  4. live modeではブラウザ乱数cascadeを完全に止める。manual STIMULATEはDEMO/REPLAYと明示し、backend state/metricsへ絶対に書かない。
  5. 右HUDにFIELD STATE、DECISION TRACE、選択nodeのactivation内訳、certificate、reason code、LEGENDを追加する。
  6. 刺激はorange coreの二段pulse。spreadはwhite-hot coreとyellow/gold tailを持つedge path長8〜15%のtraveling electric arcとして実edge上を120〜250ms/hopで走らせ、先端に小さなbranch discharge、到着nodeにyellow flash、その後violet haloを残す。
  7. electric arcの太さ・輝度・速度は実activation deltaへ単調に対応させる。jitter/branch形状はevent seq + edge idから決定的に生成し、別nodeへ接続せずReplayで同じ形にする。休止edge全体の黄/白化、実eventのない雷、別edgeへの見せかけ伝播を禁止する。
  8. reject/inhibitはblue/cyanの内向き収縮ring + reason glyph、commitはgreen ringで描く。redはField unavailable、timeout、corrupt snapshot、seq gapなど実障害だけに予約する。
  9. Observatoryの既存Recall panelへField mode、active/candidate/commit/reject、teacher agreement、field latency、stale/offlineを要約し、クリックでCortexへ移動する。
  10. recent session selectorを追加し、session hashを表示する。異なるsessionの活性を暗黙に混ぜない。
  11. reduced motionでは移動雷をactual edge上の静的yellow arrow + arrival outlineへ置換する。Pause motion、keyboard Explorer、active-node table、ARIA summary、色以外のring/icon/state文字も実装する。

受入ゲート: 受信spread eventとyellow electric arcが1対1で、source→target、edge、開始/到着、deltaを追跡可能。線全体の点灯を「発火」に見せず、青い抑制と赤い障害を混同しない。Field unavailable/stale/seq gapで偽発火なし。event-to-paint p95 ≤250ms、通常45fps以上、pulse queue ≤256。

Phase 5 — Contextual Anti-Index、Hub抑制、話題転換

  1. 現行query-conditioned Jaccard penaltyを基準に、reviewed false-positive/strong contradictionだけでcontextual negative centroidをshadow生成する。
  2. ignored、page_ignored、certificate rejectを単独の真負例にしない。retractionとgolden positiveを適用前に照合する。
  3. Hub penaltyはpageへの一律罰ではなく、query specificity、edge type、degree、supporting spanの有無で計算する。golden exact matchを保護する。
  4. topic shift detectorをhard-94に加えて、stable topic / pronoun continuation / abrupt switch fixtureで評価する。
  5. Anti-IndexとHub penaltyの寄与をcertificate/Field eventのcomponentsへ残し、Dashboardから理由を確認可能にする。

受入ゲート: hard-94 negative-hitを20%未満へ改善し、Recall@5を1pt以上悪化させない。retracted feedbackや無関係sessionの負例がscoreへ影響しない。

Phase 6 — Field候補経路の段階昇格

  1. recall.field.mode = off | shadow | candidate | activeとsession hash canaryを追加する。既定はshadow。
  2. stable topicではField top 20〜30をsemantic_client.verify(query,page_ids)で照合し、Recall Processorへ渡す。低一致・新entity・topic reset時は即full searchする。
  3. candidate modeでもfull teacherを並列shadow実行し、Field漏れ・順位・fallback・E2E commit差分を継続記録する。
  4. 5% → 25% → 100%のcanaryごとにlocked evalとlive decision traceを確認し、悪化時は自動的にshadowへ戻す。
  5. Field候補だけでcertificateを省略しない。Fieldは高速なbranch predictor、Recall Processorはretire/commit境界という役割を維持する。

受入ゲート: stable-topic turnでteacher-committed pageがField top30に99%以上含まれる。最終注入Precision/Recallがteacher比1pt以内の非劣化、4秒超過0、full-search率とp95がbaselineより改善。条件未達ならshadowのまま完了扱いにしない。

Phase 7 — ラベル工場、学習Field、Recall Compiler

  1. certificate、pull/read、recall_used、明示評価を一つのprovenance付きlabel ledgerへjoinし、silver/strong/goldの重みと重複排除を固定する。
  2. strong positiveが200件未満、または十分なsession分散がない間はField edge weightを自動学習しない。gate/calibrationは既存どおり500件未満で適用しない。
  3. 時系列holdout、policy history、変更幅cap、last-known-good、自動rollbackをRecall Field/selectorにも適用する。
  4. claims.pyを利用してentity/relation/value/time/sourceへ型付けするRecall Compilerをshadow追加し、構造化可能な質問は意味アドレスexact hitで候補化する。
  5. Recall Compilerは矛盾・superseded・時制・source digestを検証し、曖昧な文章記憶は必ず通常のNemotron+BGE経路へfallbackする。
  6. 常時Shadow Teacherでfast pathと最高品質pathの不一致を収集し、採用ゲートを一度きりの94件から実trafficへ拡張する。

受入ゲート: 学習とholdoutのsession/query漏洩なし。Recall Compiler exact-hitのPrecision 99%以上、coverageを別表示。fast pathはteacher非劣化を満たすまでproduction authorityにしない。

Phase 8 — 挑戦者比較（採用は勝ったものだけ）

  1. ColBERT late-interactionを別index・別feature flagで実験し、BGE serviceと同じmanual-94/locked/full評価、MPS latency、index容量、incremental更新を比較する。
  2. decoder judgeのprefix KV cacheはsupporting spanと固定promptだけをmodel/revision/template/position digest付きLRUで試す。全ページKV保存は禁止する。
  3. ANE query encoder蒸留はteacher top-50再現率99%以上を採用条件とし、CPU BM25・ANE query・GPU BGEの同時実行が共有メモリ競合を含め本当に速いか計測する。
  4. DSI、記憶LoRA、誤った先行注入はproduction候補から除外する。再検討する場合も独立lab planを要求する。

受入ゲート: 挑戦者は品質非劣化かつE2E p95/資源使用量で明確に勝つ場合のみ採用。勝者なしを正当な結果として記録する。

Phase 9 — ドキュメント、GitHub runtime、live完了確認

  1. docs/architecture.md、docs/hooks.md、docs/config.md、docs/operations.mdへservice topology、budget、Field state、dashboard、rollbackを反映する。
  2. 各Phaseを意味のある単位でcommitし、計画書checkboxと実行ログを完了直後に更新する。ユーザー既存の未追跡ファイルをcommitへ混ぜない。
  3. push/restartの明示許可後、GitHub-backed runtimeを更新し、Dashboard、Semantic、Reranker、Hook、必要なworkerを再起動する。
  4. runtime archiveのdirect_url.json commit、running process/module path、service health、socket、Dashboard runtime commitをGitHub HEADと照合する。

受入ゲート: GitHub commit、runtime archive、running process、health、live Recall、live Cortexが一致。ローカルworktreeだけを見てproduction完了と報告しない。

実行中更新ルール

  • 実行手順のチェックは、各手順の完了直後に更新する（まとめて更新しない）。
  • チェックを更新したら、同時に 実行ログ へ時刻付きで追記する。
  • 中断時は 状態（plan-meta の JSON および .badge の data-state）を blocked にし、理由を ブロッカー に記入する。
  • 各Phase開始前に前Phaseの受入artifactを読み直す。前提数値を記憶や古いページから転記しない。
  • 品質契約、性能契約、UI契約を別々に検証し、「テストが通った」だけで品質・速度・見た目の完了を宣言しない。
  • shadow/canary結果が悪い場合は、そのPhaseを無理にproductionへ昇格せず、失敗結果を計画書へ残す。

やってはいけないこと（必須）

  • 発火値、co-fire exposure、prefetch exposure、カード表示回数を「正しい記憶」のラベルとして扱わない。
  • 未検証の投機候補をhost contextへ先行注入しない。次ターン訂正をrollbackとして扱わない。
  • Field候補、BGE順位、9B judgeのいずれか一つだけでcommitしない。certificate境界を迂回しない。
  • ignoredを無条件の負例、certificate passをgold、certificate failを真負例へ昇格しない。
  • 過去3発言を検索queryとしてそのまま混ぜない。異なるsessionやtopic epochの活性を暗黙に混ぜない。
  • live Cortexでブラウザがランダム伝播を生成しない。demo/replayをlive表示に見せない。
  • Dashboard artifactへraw prompt、query全文、supporting span、ページ本文、sensitive metadataを露出しない。
  • BGEとNemotronを同じprocessへ詰め込み、障害・restart・resource pressureを連鎖させない。
  • 同期Hookの4秒deadline、600ms deterministic fallback、circuit breaker、fail-openを弱めない。
  • 既存BM25/Nemotron経路、旧selector、Field off/shadow fallbackをcanary完了前に削除しない。
  • ColBERT、KV cache、ANE、学習rankerを「革命的だから」という理由だけでproduction採用しない。
  • UI完了をスクリーンショットの印象だけで判定しない。指定viewportでDOM寸法・重なり・overflowを実測する。

完了条件

  • Recall Processorが常駐BGEとページ別Evidence Certificateを使い、0〜6件のcertified pointerをcommitし、そのうちrich evidenceは最大2件にする。件数はmarginal utilityとtoken budgetで止まり、低信頼時は0件を返す。
  • 同期E2E p95 < 3.5s、4秒超過0。Reranker/Field/model unavailable時もhost promptはfail-openで継続する。
  • locked評価の注入Precision目標90%以上、hard-94のRecall/negative-hitが基準非劣化。abstentionと関連記憶Recallを同時に満たす。
  • Fieldは最低shadowで全turnを追跡し、昇格条件を満たした場合のみcandidate/activeになる。単独commit経路は存在しない。
  • Cortexの表示は実Field event/stateと一致し、live modeでランダム発火を生成しない。ObservatoryにもField健康状態が出る。
  • orange刺激、yellow electric arc伝播、violet残留活性、green commit、blue reject/inhibit、red faultが色、形、動き、ラベルで区別でき、指定viewport・reduced motion・keyboard/非Canvas経路を検証済み。
  • certificate labelのsilver/strong/goldが分離され、サンプル不足時に学習・較正が走らない。
  • 各feature flag、last-known-good、service fallback、Field shadow rollbackが実際に動く。
