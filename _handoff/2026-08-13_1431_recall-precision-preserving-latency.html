Plan: Chronovisor Recall 精度維持型レイテンシ最適化

running plan_cef89aa67e5b4ef99e4b51890b402a60 2026-08-13T14:31:31+09:00

目的

  • L2 Automatic Recall の4秒契約を維持しながら、正常系のsemantic・graph・teacher・authoritative rerankerによる検索精度と順位を変えずに高速化する。
  • 順位に影響しない重複refresh、Field/compiler/processor shadow、診断writeを権威検索より後へ移し、浮いた時間を精度に寄与する処理へ優先配分する。
  • 正常系が間に合わない場合だけ、既存の永続SQLite BM25 projectionとL1 contextを使う決定的fallbackへ切り替え、現在の pages=0 timeoutより有用なdegraded結果を600ms以内に返す。
  • 速度改善を精度低下との交換条件にせず、正常系のtop-k/reranked order parityとlive注入品質をhard gateにする。

現状と根因（2026-08-13）

  • 以前は実際に動作していた。7月30日〜8月2日の成功L2中央値は約1.0秒、8月11〜12日も3ページを注入する実成功が残る一方、中央値は約2.7秒まで悪化した。
  • 直近400件はtimeout 216件、成功172件。Field p50約338ms、teacher search p50約248ms、reranker p50約643ms。直近失敗は evidence_search 中に内部deadlineへ到達している。
  • max_queries=3 は件数上限であり時間予算ではない。増加しても改善せず、複数query時は悪化し得る。
  • queries=[] はquery未生成の証拠ではない。検索例外後のtimeout resultが公開用queriesを空配列で再構築している。remaining_ms≈473 もfallback開始時点の古いtelemetryである。
  • 正常系は4秒からheadroom 250msとfallback reserve 600msを除いた約3150msで打ち切られる。現fallbackは同じRecall実装へ再入場し、Field、compiler、teacher search、reranker周辺、診断writeを再実行して約600msを自分で消費する。
  • 正常検索はBM25 projectionのbuild/stat walkを繰り返し、検索結果 pre_results が既にあるcontext生成でもstore refreshを再実行する。これは順位を改善しない重複処理である。
  • 現在のFieldはcandidate、compilerとrerankerはshadow運用で、返却authorityまたは順位を変更しない。これらを残予算従属にしても現行の正常回答精度は変わらない。

目標アーキテクチャ

  • Full path: fused teacher（BM25 + semantic + graph）→ 選択中のauthoritative reranker → sensitive/lifecycle filter → context render。
  • Post-authority: Field/compiler/processor/evidenceなど非権威shadowと診断writeは、返却結果が確定した後に残予算がある場合だけ実行する。
  • Degraded path: primary deadline到達時は処理全体を再実行せず、L1 + build済みSQLite BM25を直接queryし、同じfilterとrendererで返す。semantic、graph、reranker、Field、compiler、observer、teacher queue、index refresh、writeは呼ばない。
  • Cache unavailable: BM25 projectionが無い・不正・期限内に読めない場合は再構築せず、L1-only degradedまたはhost no-opへfail-openする。
  • Authority future-proofing: Fieldやrerankerがsealed active authorityへ昇格した場合は通常経路を維持し、勝手にskipしない。skipは現在のcandidate/shadow、または明示的degraded結果に限定する。

やってはいけないこと（必須）

  • 通常経路からsemantic、graph、teacher、authoritative rerankerを恒久的に削除して速度を作らない。
  • max_queries や total_timeout_ms を増やして根治扱いしない。
  • 新しいcache frameworkを作らない。既存の永続SQLite BM25 projection、L1 context、filter、rendererを再利用する。
  • fallback中にindex build、store refresh、model call、shadow観測、権威state更新、同期writeを開始しない。
  • 正常系とdegraded系を同じ成功指標に混ぜない。ok と degraded、authority、search modeをログで区別する。
  • 速度だけで採用しない。正常完了ケースの候補集合、top-k、reranked order、sensitive filter、context blockが一致しなければrollbackする。

前提・仮定

  • 本Planは既存の recall-l2-timeout-hardening P0/P1とは別の新規計画であり、そのdeadline分離・単一absolute clock・I/O guardを前提にする。
  • L2 outer 4000ms、engine 3750ms、fallback reserve 600ms、host wrapper 7000msは変更しない。
  • 正常精度の正本はteacher/full fused searchと、その時点でauthoritativeに選択されたreranker結果である。shadow出力は品質比較に使えるが返却authorityではない。
  • fallbackの目的は正常系を置き換えることではなく、正常系が期限を超える場合に pages=0 を避けることである。
  • 既存BM25 projectionの鮮度・schema・失敗時挙動を確認し、fallbackでの再buildは行わない。

実行手順

  1. P0-A — baseline固定: 固定cohortで正常成功、timeout、Field、teacher search、reranker、context renderの件数・p50/p95/p99・top-k・注入pageを保存し、正常系とdegraded系を分けて比較可能にする。
  2. P0-B — stage timingの穴を埋める: 既存Recallログへcleanup、session load、Field、compiler、BM25 build/query、semantic、graph、verify、reranker、context、finalizeの匿名所要時間を追加し、本文・query本文・page本文は記録しない。
  3. P1-A — fallbackを直接経路化: run_deterministic_fallback() から通常の _run_recall_impl() 再実行を外し、既存L1とbuild済みSQLite BM25の直接queryだけでdegraded contextを組み立てる。
  4. P1-B — filter/render再利用: fallback候補にも正常系と同じsensitive/lifecycle filtering、dedupe、whole-block rendererを適用し、authorityと search_mode=bm25-fallback を明示する。
  5. P1-C — fallback副作用ゼロ: fallbackでField、compiler、semantic、graph、reranker、processor、evidence observer、teacher queue、index refresh、diagnostic/durable writeが一度も呼ばれない回帰テストを追加する。
  6. P2-A — 重複refresh削除: teacherの pre_results が既にあるcontext生成では二度目のstore refresh/searchを省き、ContextItem、filter結果、renderer出力が修正前と一致することを固定する。
  7. P2-B — authority-firstへ並べ替え: fused teacherとauthoritative reranker、filter、context確定を先に行い、candidate/shadow Field、compiler、processor、evidence、診断処理は残予算内のpost-authorityへ移す。
  8. P2-C — authority保護: sealed active Field/rerankerでは既存fail-closed semanticsを維持し、candidate/shadowのみskip可能であることをmode別testで固定する。
  9. P3 — 精度parity: baseline cohortを修正前後でpaired replayし、正常完了ケースのcandidate set、teacher top-k、authoritative reranked order、注入contextを100%一致させる。差があれば性能値にかかわらず採用しない。
  10. P4 — live canary: push後、Codexを先行canaryし、最低24時間かつ100 eligible promptsでok/degraded率、outer timeout、p95/p99、注入率、page/context coverage、normal/degraded比率を観測する。
  11. P5 — 収束: Exit Criteriaを満たしたcommitだけをmainへ正本化し、Planのcheckbox、実行ログ、状態、runtime archive commitを同期する。未達の段階だけ独立revertする。

完了条件

  • 正常完了ケースのcandidate set、teacher top-k、authoritative reranked order、sensitive filtering、注入contextがbaselineと100%一致する。
  • fallbackは600ms以内に終了し、Field/compiler/semantic/graph/reranker/processor/observer/queue/refresh/writeを呼ばない。BM25 cache不在時も再buildせずL1-onlyまたはhost no-opで終了する。
  • 外側SIGALRM timeout=0、host-wrapper timeout=0。eligible promptは4秒未満で ok または明示的 degraded を返す。
  • 正常成功p95 <= 3000ms、p99 <= 3400ms。canaryは最低24時間かつhost別100 eligible prompts以上。
  • baseline比で decision=read/injected 率、page/context coverage、既存quality metricが悪化しない。正常系parityは差分ゼロを要求する。
  • degraded結果は現行timeoutの pages=0 より有用で、取得hitがある場合は少なくとも1つの安全なcontext blockを返す。
  • targeted tests、isolated Recall tests、Ruff、py_compile、git diff --check、runtime archive SHA、live hook commitがすべて一致する。

即時ロールバック条件

  • 正常系のtop-k、reranked order、filter、contextに1件でも意図しない差分が出た場合。
  • host-wrapper timeoutが1件でも発生、または30 eligible prompts後のouter timeout率が1%以上の場合。
  • degraded経路がindex build、model、shadow、writeを開始した場合。
  • BM25 cache破損・欠落時に4秒を超える、またはunsafe/sensitive pageを注入した場合。
  • rollbackはP1 fallback、P2 refresh、P2 authority順序を独立単位で行い、4秒/3750ms/600ms設定は変更しない。

検証手順

  • tests/test_recall_runtime.py: primary deadline後もfallbackが600ms内に返り、重いsubsystemを呼ばず、cache hit/L1-only/cache invalidの各結果を固定する。
  • 正常系paired replay: 修正前後のteacher候補ID・score順、authoritative reranker順、ContextItem、rendered blockを機械比較する。
  • mode matrix: Field candidate/shadow/active、reranker off/shadow/canary/onで、authorityとskip可否が期待どおりか確認する。
  • slow component試験: BM25、semantic、graph、reranker、filesystemを個別に遅延させ、正常系またはdegraded系が4秒内で決定的に収束することを確認する。
  • 隔離rootで関連suiteを実行する: CHRONOVISOR_ROOT="$(mktemp -d -t chronovisor-test)" uv run pytest -q ...。
  • live canaryではnormal/degradedを分離し、latency、outer timeout、search mode、injected pages、coverage、authority driftを固定baselineと比較する。
