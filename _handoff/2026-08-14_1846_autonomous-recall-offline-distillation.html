Plan: Chronovisor 自律Recall：オフライン教師蒸留・継続学習・高速配信

ready plan_85e0b9241c9e4107b6bbae9aedf2eb33 2026-08-14T18:46:47+09:00

目的

  • 数か月分の committed Raw 会話履歴から「その時点の質問に、過去の何を出すべきだったか」を完全自動で再構成し、Recall の教師データを作る。
  • 重いローカルLLM三者はオフラインだけで使い、ライブ経路は既存の BM25・semantic・graph と小さな校正器だけにして、精度と 0.x 秒台の応答を両立する。
  • 新しい Raw が増えるたびにデータ、評価、ポリシー候補を増分更新し、時系列 holdout、shadow、canary、自動 rollback を通過したものだけを無人で昇格する。
  • 現在の「注入されたが無視された」を成功・失敗の正解として扱わず、時点整合性、構造リンク、その後の訂正・再質問・test failure・rollback など検証可能な結果から学習する。

設計判断（結論）

採用案は「オフライン三教師 + 構造検証 + 小さなライブ学生」。 モデル合議そのものを真実にせず、Raw の provenance、時系列、exact link、後続 outcome で確定した行だけを昇格判定の正解データにする。教師だけの判断は分離したuntrusted train層で候補ポリシーへ使えるが、verified-only holdout/canaryを独立に通るまで本番ポリシーを動かさない。
  • 初期版では fine-tune しない。既存の純 Python logistic/calibrator と検索 feature を拡張し、重み・threshold・abstain margin の小さな immutable artifact を作る。
  • 三教師の主担当は query/candidate pair の固定 hash bucket で決定的にほぼ三等分する。固定 15% の probe だけを三者共通評価にし、model drift と calibration を測る。
  • 事実・index は Raw commit 後すぐ増分反映する。ランキングポリシーは turn ごとに書き換えず、24時間または十分な新規 verified label が溜まった時だけ batch 更新する。
  • 人間の確認、gold 作成、採否ボタン、明示 feedback は昇格経路に置かない。通常会話で自然発生した訂正等は outcome 証拠として使えるが、ユーザーへ評価作業を要求しない。

やってはいけないこと（必須）

  • ライブ L2 の authoritative path から local teacher、frontier model、rewrite/judge/reranker、全 Raw scan、学習処理を呼ばない。timeout を延ばして問題を隠さない。
  • query 時刻より後の Raw、同一 session 内で query event 以後の event、legacy から捏造した atom を候補・feature・教師入力へ混ぜない。
  • 三者一致、多数決、model confidence、ユーザーの沈黙、会話終了、単なる used/ignored を正解 label にしない。
  • secret/credential、明確な PII、仕事・会社・顧客の非公開情報、Raw 本文を remote route へ出さない。Raw を読む教師は local-only を実行前に強制する。
  • 生 query、Raw span、prompt preview を dashboard、metrics、policy registry に複製しない。参照は raw id/range/hash と query hash に限定する。
  • 全件 abstain で誤注入率だけを良く見せない。coverage と strong-anchor rescue を同時 gate にする。
  • 候補 policy が通る前に現行経路を削除しない。まず off/shadow 化し、rollback 後も LKG へ戻せる状態を保つ。
  • 初期版で neural reranker、embedding fine-tune、vector DB、新しい orchestration framework を追加しない。既存資産で不足が実測されるまで作らない。

前提・仮定

  • 正本は committed Raw v2。RawStore(..., mode="v2") と既存 transcript semantic projection を使い、system/developer/AGENTS injection、thinking、injected context を除外した user event を query にする。
  • Campaign Y の EpisodeProjection、EvidenceAtom、EvidenceLedger、RetrievalProgram、Raw hash/range 検証を再利用する。ただし QueryManifest は user Raw event から別抽出し、現行契約どおり user発話を authoritative EvidenceAtom にしない。
  • 現行 BM25/anchor、semantic generation、graph/entity path、Recall candidate trace、純 Python logistic/calibrator、atomic pointer/LKG、sleep cycle、deterministic canary を再利用する。
  • 教師モデル名は固定しない。stable role recall.distill.teacher.{a,b,c} に local model route を割り当て、route identity・model version・prompt hash を ledger に残す。
  • 初期 backfill の件数、現在の正確性/coverage/latency は P0 で凍結する。以後の gate は同じ immutable query cohort と chronological unseen window で比較する。

データの作り方

0. Feasibility preflight

  • P0で archive拡張子ではなくRawの実shape/receiptを検査し、event indexと時刻を持つnative user query数、期間、host/session分布、exact structural/outcome link数、verified positive/negative発生率を数値化する。
  • P5以降へ進むhard floorは、eligible native query 1,000件以上・30日以上・3つ以上の時系列window、verified label 500件以上・各class 100件以上、かつpower analysisが要求する件数の大きい方とする。
  • 不足時はP1–P4のcapture/backfillだけを継続し、trainer・shadow・canaryへ進まない。教師多数決、人手gold、legacyからの推測で不足を埋めない。

1. Query manifest

  • native Raw v2 の semantic projection から role=user かつ non-empty の event を抽出する。query id は host/session_key/raw_id/event_index/raw_sha の canonical hash とする。
  • 各 query に as_of、source event index、raw receipt、semantic text hash を保存する。本文は manifest に複製せず、教師実行時だけ private RawStore から再読する。
  • QueryManifest は質問の正本であり evidence authority ではない。候補 Evidence は現行契約どおり assistant/tool/receipt に裏付けられた atom だけにする。
  • 同一内容の再実行は同じ id を返し、cursor は committed Raw watermark までしか進めない。

2. Historical index と point-in-time candidate snapshot

  • 候補条件は atom.validity.end < query.time、または同じ Raw/session の場合 atom.event_index < query.event_index。同時刻は event index で裁定し、future leakage を fail-closed にする。
  • current Page/BM25/semantic/graph index は query 後の更新を含むため、historical replay へ直接使わない。Raw/EpisodeProjection の assistant/tool atom だけから derived SQLite FTS5 index を watermark単位で決定的に構築し、atom id、validity、event index、exact path/commit/task/entity refs を保持する。
  • 候補は exact anchor、historical FTS BM25、receipt-bound relation を union し、教師用だけ top-K 100–300 を snapshot 化する。主担当教師が query から出した少数の検索語/entity cueで同じ historical index を再検索してよいが、追加候補も同じ as_of filter を通す。
  • 初期版に別vector DBは作らない。lexical candidate recall が P0 gate を満たさない時だけ、同じatom集合から作るimmutable offline embedding generationを追加計画する。
  • candidate id、channel rank/score、atom/page refs、provenance、pool hash、retriever revision を保存する。候補生成と教師判定を分離し、後から同じ pool を再生可能にする。
  • historical FTS rank/scoreはcandidate discovery用であり、そのままstudent featureにしない。student featureはoffline/liveが同じ純粋関数とschema revisionで再計算できるものだけにし、byte-identical feature parity testを通す。
  • legacy archive、authority 不明、provenance 不一致、high-sensitive remote route は unknown/reject とし、学習対象へ入れない。

3. 三教師の割当

  • SHA-256("assignment-v1\0" + query_id + "\0" + candidate_id) の固定bucketで主担当を決定的にほぼ均等化する。別の固定 probe-v1 bucketの15%だけ他の二教師にも送る。route/model更新でbucketを変えず、許容load skewはP0で固定する。
  • strict JSON は relevant | irrelevant | uncertain、最小 atom ids、短い理由、route identity、model/prompt revision を返す。入力は P0 で固定した最大bytes、最大候補数、候補ごとの最大Raw spanを越えない。parse failure は再試行せず uncertain。
  • 三者一致は model drift の観測値であり label authority ではない。probe の disagreement、flip rate、per-route calibration を比較し、劣化した route は自動停止できるようにする。

4. 自動確定 label

区分例扱い
strong positivesame_raw_session_before_index、exact normalized path、full commit SHA、task UUID、candidate atomへexact joinできるtool/test receipt、verified supports閉じたpredicateとprovenance/時系列検証をすべて通れば学習・昇格 authority あり
hard negativeexact project/task mismatch、wrong time、verified supersedes/contradicts/reverts、注入receiptとexact joinできる訂正・再質問・rollback閉じたpredicateとoutcome receiptを検証できる場合だけauthorityあり
teacher-onlyモデルは関連/無関係と判断したが exact anchor/outcome がない分離したuntrusted train層で重み上限付きのchallenger作成にだけ使える。validation/test/metric truthにはせず、verified-only gateなしに昇格させない
uncertain/reject根拠不足、教師不一致、時系列不明、provenance failure、legacy source学習から除外。捨てずに ledger へ理由を記録

「訂正がなかった」「返答後に会話が終わった」は positive にしない。synthetic query は regression test 専用で、昇格 authority を持たない。

「同じtaskらしい」「testの後にfixが来た」「toolが成功した」だけでは因果を認定しない。上のexact predicateへ落ちないものはteacher-onlyまたはuncertainにする。

5. 分割と漏洩防止

  • 同一 session/task/entity cluster を一つの connected component として分割し、train より後に embargo、validation、さらに後ろに locked test を置く rolling-origin split とする。
  • 後続 event は label の outcome 証拠には使えるが、query 時点の candidate/feature へは絶対に戻さない。
  • feature whitelist を固定し、query 後にしか得られない used、answer text、future entity、future timestamps を student input から排除する。

ライブ学生と速度設計

  • 新しい model service は作らず、recall_runtime.py の既存 build_evidence_features()、calibrated_score()、decision_from_score() を拡張する。
  • feature は exact anchor、entity overlap、same session/task/cwd、temporal validity/decay、superseded、graph path、top1/top2 margin等、offline/liveの同じpure functionで再現可能なwhitelistに限定する。historical FTS固有scoreは除外し、channel rank/scoreはparity testを通ったrevisionだけ許可する。
  • P6a の authoritative path は既存 readonly lexical index の BM25/anchor だけで開始する。student は active JSON の重みを一回計算し、threshold と margin を越えた 0–3 cards だけ返す。
  • 現行 semantic/graph pipeline は逐次かつ semantic timeout が live SLO より長いため、初期 authorityへ入れない。shadowで追加価値が実測できた時だけP6bとしてsingle deadlineの並列fan-outへ変更し、残りbudget内に完了した結果だけを加える。待たずにBM25へfallbackする。
  • 新policyでは既存 usage_prior weightを0、旧 negative_feedback stageをhard offにし、verified ledger以外からscoreを動かす経路を残さない。
  • SLO は end-to-end p50 ≤ 400 ms、p95 < 900 ms、hard deadline 1,200 ms、timeout < 1%。deadline 超過を timeout 延長で解決しない。

継続学習ループ

  1. Raw commit 後、sleep cycle の既存 bounded background lane が watermark 以後の新規 user query を少量ずつ manifest 化する。
  2. 各 cycle で point-in-time pool を作り、三教師の決定的 shard と probe を処理する。foreground Ollama lease を最優先し、teacherは次chunk取得前に譲る。in-flight generationは短い上限内で完走させるか結果を破棄し、pause/resume可能とは仮定しない。
  3. structural/outcome verifier が label を確定し、ledger head と cursor を seal する。失敗はその chunk だけ再開可能にし、cursor を先送りしない。
  4. 24時間または preregister 済みの最小 verified label 数に達したら candidate policy を作る。単一 event ごとに重みは変えない。
  5. rolling-origin replay を通過した candidate だけ shadow へ出す。shadow 合格後、session hash で 5% → 25% → 100% と段階昇格する。
  6. 各段階で自動 gate が悪化を検出したら active pointer を LKG へ戻し、原因 run を quarantine し、学習を自動停止する。live 検索は LKG で継続する。

実行手順

  1. P0 — Baseline と契約を凍結する。 native query/期間/host、verified label発生率、candidate recall、wrong-domain injection、strong-anchor rescue、coverage、abstain、p50/p95/timeoutをimmutable artifactへ記録する。hard floor、power analysis、feature whitelist、closed predicate、teacher schema/input上限、load skew、fixed cohort/min events/CI/window、昇格閾値、privacy preflightを固定する。
  2. P1 — Historical query/candidate dataset を実装する。 Raw v2から別QueryManifestを増分生成し、assistant/tool EpisodeProjectionだけのderived FTS5を固定tokenizer/normalizer revisionで構築する。current Page/semantic/graphを使わず、queryより前だけのwide poolを再現可能なsnapshotとして保存する。
  3. P2 — Structural/outcome verifier を実装する。 Raw hash/range、event index、exact path/full SHA/task UUID、receipt-bound tool/test、verified supports/contradicts/supersedes/revertsの閉じたpredicateだけでstrong positive/hard negative/uncertainを決める。
  4. P3 — 三教師 batch を実装する。 stable local roles を決定的に三分割し、固定15% probe、strict output/input上限、route/prompt revision、local-only preflight、foreground lease、再開可能cursorを通す。
  5. P4 — Append-only dataset と rolling-origin split を実装する。 hash-chain ledger、cluster dedup、embargo、validation/locked test、future feature exclusion、offline/live feature parityを実装する。teacher-onlyは重み上限付きuntrusted train層、uncertainは完全除外として隔離する。
  6. P5 — 初期 student policy を作る。 既存 logistic/calibrator を新 verified features で再計算し、fine-tuneなしで immutable weight/threshold artifact と LKG pointer を生成する。
  7. P6 — ライブ fast path を実装する。 P6aはBM25/anchor + tiny policy + 0–3 cards/abstainでSLOを満たす。semantic/graphはshadowに置き、価値を証明した場合だけP6bのsingle-deadline並列fan-outへ進む。usage prior/negative feedback/sync model/Raw scanをauthorityから外す。
