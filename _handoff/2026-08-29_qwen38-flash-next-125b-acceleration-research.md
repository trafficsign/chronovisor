# Qwen3.8 Flash-Next 125B / oMLX 0.6.3 高速化調査

調査日: 2026-08-29

対象: Apple M4 Max (128 GB unified memory), oMLX v0.6.3 (MLX 0.32.0), `Jundot/Qwen3.8-Flash-Next-oQ4e-mtp`, `config.model_type=qwen4_exp`
既存ベンチ条件: q4e、`mtp_enabled=true`、`mtp_num_draft_tokens=3`、`qwen4_ple_ssd_offload=true`、TurboQuant=false、DFlash=false、ANE 設定キーなし（既定 false）。

## 結論（先に採用順）

1. **現行の q4e + Lightning MTP (adaptive max depth 3) + PLE mmap を維持する。** oMLX 0.6.3 の公式リリースは Qwen3.8 q4e を first-class 対応し、M3 Ultra で MTP により decode が 2.33--2.62 倍、受理率 96.8--97.9% になることを公開している。ただしこれは M3 Ultra の上流実測であり、M4 Max での最終値ではない。[oMLX v0.6.3 release](https://github.com/jundot/omlx/releases/tag/v0.6.3)
2. **ANE/GPU hybrid prefill を採用する。** ローカル tuner は 2,048-token 固定形状で **49 MLP + 36 GDN procedure** の dual-ANE compile を完了し、GPU-only 441.2 tok/s に対する predicted optimum を 629.5 tok/s（+42.68%）とした。[ローカル tuner 結果](/Users/trafficsign/projects/sandbox/chronovisor-qwen-next-bench/runtime/q4e-accel-search/ane-tuner-result.json) 独立した cache-off 3回中央値では ANE off 比で 4K **+9.7%**、16K **+11.2%**、32K **+10.2%**、needle 9/9、swap増分0だったため、採用判断には tuner 予測ではなくこの約10%を使う。[独立実測JSON](/Users/trafficsign/projects/sandbox/chronovisor-qwen-next-bench/runtime/q4e-accel-search/ane-on-performance.json)
3. **prefix cacheを採用し、concurrencyは1に固定する。** 16K共通prefixでは cold 28.27秒に対し warm 4.57/3.90秒、再起動後5.44秒、`cached_tokens=14336` を確認した。一方、4K×2は逐次13.40秒に対し concurrency 2で13.67秒と改善せず、個別待ち時間が10.36/13.64秒へ悪化した。したがって SSD 5GB + hot 2GB のcacheを有効にし、単一要求の体感速度を優先して concurrency 1を使う。[server log](/Users/trafficsign/projects/sandbox/chronovisor-qwen-next-bench/runtime/q4e-accel-search/logs/server.log)
4. **TurboQuant、DFlash/DFlash2、SpecPrefill、Qwen4 QSA 用でない汎用 KV quantization は本番採用しない。** 0.6.3 に機能自体はあるが、Qwen4 の QSA cache/indexer 状態を保つ実装・125B parity がない。`enabled=true` や「patch loaded」だけでは実効を意味しない。
5. **Qwen 固有 kernel は、実行ログを伴うものだけ段階的に採用する。** `qwen35_moe_gate_up` はソース上 `qwen4_exp` を明示的に許可し bit-exact と説明されているため第一候補。weighted-sum/GDN/FA256/q4-MLP は継承経路で適用される可能性はあるが、qwen4_exp の実測がないためログ確認が必須。

## 一次情報と適用範囲

- oMLX v0.6.3 の依存は MLX 0.32.0、Qwen3.8、PLE、Lightning MTP、prefix/SSD cache、structured tool call を含む。[release](https://github.com/jundot/omlx/releases/tag/v0.6.3)、[README](https://github.com/jundot/omlx/blob/v0.6.3/README.md)、[model settings](https://github.com/jundot/omlx/blob/v0.6.3/omlx/model_settings.py)
- Qwen の公式カードは 125B total / 6B activated、51B n-gram PLE、4B MTP、48 layers、512 experts、native context 262,144（1M へは YaRN）と記載する。[Qwen model card](https://huggingface.co/Qwen/Qwen3.8-Flash-Next)、[Qwen official repository](https://github.com/QwenLM/Qwen3.8-Flash-Next)
- Apple の M4 Max 128GB 構成は 16-core CPU / 40-core GPU / 16-core Neural Engine / 546 GB/s memory bandwidth。[Apple Mac Studio (2025) technical specifications](https://support.apple.com/en-us/122211)
- oMLX の qwen4_exp 実装は GDN と QSA の hybrid cache、独自 indexer、PLE を持つ。[qwen4_exp compatibility registration](https://github.com/jundot/omlx/blob/v0.6.3/omlx/patches/mlx_vlm_qwen4_exp_compat/__init__.py)、[qwen4_exp language implementation](https://github.com/jundot/omlx/blob/v0.6.3/omlx/patches/mlx_vlm_qwen4_exp_compat/vendor/mlx_vlm/models/qwen4_exp/language.py)
- 上流の Qwen3.8 q4e benchmark は M3 Ultra の fresh process であり、M4 Max へ数値を外挿しない。以下では「上流の機能/証拠」「この M4 Max のローカル一次実測」を分ける。

## M4 Max での最小実測計画（結果反映済み）

### 固定条件

- fresh process と warm process を分け、同一 model revision（q4e artifact）、同一 tokenizer/chat template、同一 prompt token IDs、同一 `max_tokens` を使う。
- benchmark は deterministic (`temperature=0`/固定 seed) と本番 sampling/structured schema の二系統。速度用の deterministic 結果を品質結果と混ぜない。
- まず 2,048/4,096/16,384/32,768 prompt tokens、completion 128 tokens。Qwen の 262,144 native ceiling を超える試験は別扱いで、YaRNを短文試験に持ち込まない。
- ANEの主要contextは各3回中央値、prefixはcold/warm/restart、concurrencyは異なる4K×2の逐次/同時で最小A/Bした。M3 Ultra公式値は比較の目安であって閾値ではない。

### A/B順序（競合を混ぜない）

1. **Baseline（完了）:** q4e + PLE mmap + native MTP depth3、ANE/TQ/DFlash/SpecPrefill off、prefix miss。
2. **ANE A/B（完了）:** baselineへ推奨値（`.60/.375`, `sequence=2048`, `tail=1436`, CPU/fused-down off）だけを加え、4K/16K/32Kを各3回測定。
3. **MTP depth（現設定維持）:** exact targetの公式A/Bとローカルacceptanceがdepth 3を支持するため、再選定を省略。
4. **Prefix（完了）:** 同じsystem/tool相当prefixのmiss→hit→suffix変更→restart後hitを確認。
5. **Concurrency（完了）:** 1/2を比較し2が不合格。4/8はlatency・memory悪化の見込みしかないため省略。
6. **Compile/kernel（完了）:** ANE compile cache hit、MoE gate+up 49層、関連patch applied/engaged logを採取。個別kernel toggleは追加しない。
7. **本番matrix外:** TQ、DFlash、SpecPrefill、Qwen4専用KV quantizationは、専用parityがupstreamへ入った場合だけ別計画で再評価する。

### 必須 metrics/log fields

- **性能:** TTFT、prefill tok/s（PP）、decode tok/s（TG）、first-token latency、per-request/aggregate throughput、queue wait、p50/p95。
- **MTP:** draft count、accepted count、acceptance、adaptive depth、verify time、fallback count。
- **cache:** `prefix_hits`, `prefix_misses`, `prefix_tokens_matched`, `prefix_tokens_requested`, `prefix_tokens_saved`, `target_static_hits/misses/tokens_restored`, `ssd_hot_hits`, `ssd_disk_loads`, `ssd_saves`, `ssd_errors`, `hot_cache_evictions/promotions`, API `prompt_tokens`, `completion_tokens`, `cached_tokens`。
- **ANE:** `Eagerly compiled ...`, `Warmed ... ANE procedures`, `qwen35_ane_prefill_status` (`attempted`, `configured`, `shed`, `mlp_layers`, `gdn_layers`, `dual_ane_layers`, `resident_programs`, `tail_padding_min_tokens`), `[benchmark-prefill]`, `[benchmark-ane-profile]`, `[benchmark-ane-summary]`。
- **memory/system:** `mx.get_active_memory`, `mx.get_peak_memory`, process `phys_footprint`, Metal/IOGPU wired usage/limit、oMLX memory-guard decision、swap/pagein/pageout、SSD I/O latency。
- **品質:** greedy first/last token ID、全 completion hash、hidden/logit cosine（可能なら）、long-context retrieval、structured output parse率、MTP acceptance。速度だけが改善しても token/parsing 差があれば採用しない。

## 未確定点と次の判断

- ローカル ANE tuner の +42.68% は 2,048-token fixed-shape の予測値で、採用根拠は独立4K/16K/32Kの約10%改善へ置換済み。未確定なのは114,688 token、本番structured schema、実ingest、30分p95/steady-stateだけ。
- M3 Ultra の公式 q4e MTP acceptance/TGは上流根拠、M4 Maxの短decode 63.1 tok/sと高いacceptanceはローカル補強。depth 3を既定のまま使い、depth再選定は行わない。
- TurboQuant と Qwen4 QSA auxiliary index state、DFlash target backend、SpecPrefill の Qwen4専用 draft、QSA専用KV quantization top-level routeはいずれも v0.6.3時点で未証明。
- `qwen35_moe_weighted_sum`, router, GDN/FA256/q4-MLP が qwen4_expで実際にengageする層数は、起動ログと kernel counter が得られるまで未確定。function patch がロードされたことだけでは採用しない。
- PLE artifactはsymlink 0、起動ログで `Qwen4-Exp PLE mode ...: mmap` と実ロード73.92GBを確認済み。production移設後も同じreceiptを取り直す。
- native 262Kは今回の運用対象にしない。Chronovisor上限114,688でq4e+PLE+KV+ANE+prefix hot 2GBが85GiB steady gateを満たすかをcutover前に確認する。
