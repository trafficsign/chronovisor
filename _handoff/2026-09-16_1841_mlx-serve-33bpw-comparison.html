比較結果: MLX-Serve 3.3bpwとDwarfStarの比較

done plan_ee6676bfab0c48d98f1d8b2e9f7baa9a 2026-09-16T18:41:51+09:00

結論：軽量3.3bpwは今回の条件で速く、メモリも減った

生成速度の中央値は 52.0 → 55.5 tok/s、追加メモリは約 3.7 GiB削減。16K・32K入力の初回応答も約13%短縮した。100 tok/sは今回の日本語生成では出ていない。現行以下のメモリという条件を満たしたため、次の検証に進める候補として扱う。

追加メモリはOS全体の非ファイル物理メモリの「起動前→ピーク」増分。モデル単体の専用メモリ値ではない。独立した中央値の比は+6.64%、同じ入力同士の6組の改善率中央値は+7.69%。集計方法が違うため両値は一致しない。

本番は元のDwarfStarへ復帰済み。本結果は32Kまでの固定入力と限定的な品質確認に対する結果で、262K全文投入・長時間運用・広い品質評価は未実施。macOS 27同士で構成全体を比較しており、OS更新だけの効果は分離していない。

測定条件と比較の範囲

  • M4 Max・128 GiB、macOS 27.0 build 26A428。現行→MLX→MLX→現行のABBA順。各armを別プロセスで起動し、READYの短いwarmup後に計測。
  • 両版context 262144・prefill chunk 1024・同一messages・temperature 0・seed 42。入力token数は4,045 / 16,335 / 32,719で両版一致。日本語生成は入力50・出力384 tokenで全6組一致。
  • 性能・短問ではthinking off。MLXはrootのenable_thinking=falseとenable_mtp=trueを明示。native受入はOMLXAdapter/LLMRuntime/DecisionRouterの既存ポリシーを変更せず、隔離fixtureへ適用した。
  • 現行はMTP exact、MLXは既定の厳密MTPとadaptive depth。approximate acceptance、drafter、PLDを使用していない。MLXのbuffer pool cache上限は2 GiBに固定（MLX_SERVE_CACHE_LIMIT=2147483648）。既定設定全般の性能を代表する測定ではない。
  • prefix/tokenize cacheをMLXで無効化し、全性能リクエストのcached_tokens=0を確認。MLXのngram warmは既定どおり。/propsのn_ctxとmax_safe_contextは262144、ngram warm完了を確認したが、実投入は32Kまで。
  • モデル量子化と実装が異なり、同じ重みを使ったエンジン単体の比較ではない。日本語自由生成の文章は異なる。画像・音声・コード生成・並列処理は評価対象外。

速度の再現性

生成は6組すべてMLXが高速で、5組が+3%を超えた。各順序内の3組の改善率中央値も+5.76% / +8.92%。4K入力は−3.34%と+5.30%で符号が変わり、一貫した改善とは扱わない。16K・32Kは両順序とも初回応答が短縮した。反復は少数であり、統計的な信頼区間は求めていない。

1巡目は起動・性能・短問・native受入、2巡目は起動・性能の期間を含む。両版でswap使用量の増加・swapout増加は0。MLXのモデル一式はdisk上86.36 GBで、うち約32 GBはngram用ファイル。ディスク容量と常駐メモリは区別する。

目的

M4 Max 128GB・macOS 27で、現行DwarfStar＋IQ2XXS/MXFP4Downと、MLX-Serve 26.9.3＋iQ-MLX 3.3bpwを隔離比較する。ユーザーの優先条件は現行以下のメモリ使用量。モデル量子化と実装が異なるため、実用構成全体の比較として扱う。

やってはいけないこと（必須）

本番runtime/model/config/plistを書き換えない。重いモデルを同時ロードしない。進行中Rawを強制終了しない。比較結果だけで本番採用しない。大きいmixed-4-8bit版は対象外。

前提・仮定

CLIとモデルrevisionを固定。両版context262144、同じmessages、温度0、seed42。性能・短問はthinking無効、native受入は既存の実処理ポリシーを使用。現行MTP exactに対しMLXも厳密なMTPを使用する。近似acceptanceは無効。メモリ優先のためMLXの再利用用GPU buffer cacheはMLX_SERVE_CACHE_LIMIT=2147483648（2 GiB）に制限する（128GB機の標準は8 GiB）。4K/16K/32K入力と384-token日本語生成3件、32短問、native受入4件。キャッシュ再利用と入力token差はログで検証する。

実行手順

  1. 公式CLI・モデルを隔離downloadし、hash/size/引数とharness self-checkを確認。
  2. Ingest境界・model/accelerator leaseを取得し、現行→MLX→MLX→現行の順で速度・メモリ・限定品質を計測。
  3. 本番identity・サービス・live応答を復帰確認し、結果を記録、不要な実験物を整理する。

実行中更新ルール

  • 実行手順のチェックは、各手順の完了直後に更新する（まとめて更新しない）。
  • チェックを更新したら、同時に 実行ログ へ時刻付きで追記する。
  • 中断時は 状態（plan-meta の JSON および .badge の data-state）を blocked にし、理由を ブロッカー に記入する。

完了条件

対応入力の生成速度・初回応答・入力処理速度、OS全体のwired/anonymous/compressorとfile cacheを分けて報告する。非ファイルメモリのpeakとbaseline差、swap増分を比較し、繰り返しで一貫した3%超を速度上の差とする。メモリ増加や品質/native受入の後退があれば採用候補としない。

検証手順

ローカルloopback API。プロンプトhash・completion数・cached_tokens・reasoning無効を確認する。GPU使用量はRSSだけで判定せず、vm_statとengineログを併記。メモリ圧迫やswap急増なら実験サーバーだけ止め、必ず元の構成へ復帰。元のbinary/config/plist SHA256・model metadata・サービス状態と生成canary、Semantic/Reranker live health、Dashboard HTTPを確認する。
