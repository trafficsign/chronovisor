Plan: Chronovisor Typed GraphRAG + Local Consensus Recall Calibration

done plan_fed0fc45ec8a43aa98a20220874d5495 2026-08-01T13:40:22+09:00

目的

  • 既存の BM25 + Nemotron + BGE + Recall Processor + Evidence Certificate + Stateful Recall Field を壊さず、RAGUの構造化グラフ構築思想と、少量ラベルによるJudge rubric校正思想を増分統合する。
  • ページの表層的一致だけでなく、entity・relation・communityを辿るmulti-hop候補生成を追加し、現状取りこぼしている「複数ページを横断しないと見つからない記憶」をRecallできるようにする。
  • 外部フロンティアAPIを完全に使わず、既存の Ornith 35B + gpt-oss 20B + Gemma 4 26B ローカル2-of-3合議と実利用結果をteacherにする。
  • 新しい判断結果を別の学習系へ分岐させず、既存Label Ledger、positive co-fire、Recall Field成長Controller、自動昇格・自動rollbackへ一本化する。
  • Cortexを、relation path、合議、根拠、lifecycle、実際の発火・学習を追跡できるread-onlyデバッガへ拡張する。

完成像: RAGU型Graph Builderが候補の探索範囲を広げ、ローカル合議が曖昧な関係・rubricを検証し、最終的な実使用がRecall Fieldの結合と方策を育てる。既存Recallは常にbaseline/teacher/rollback先として残す。

どの状態からも retract event で無効化可能。過去eventは削除しない。
  • proposedはDashboard/shadow traceだけ。候補順位・Field伝播・注入を変えない。
  • verifiedはcandidate branchのみ。既存teacherと並列比較し、単独注入禁止。
  • repeatedly_usedはFieldのpositive学習候補にできるが、page-level gateとrelation-level gateを両方要求する。
  • authoritativeだけがactive GraphRAG候補へ参加できる。それでも最終Page Certificateを省略しない。
  • semantic similarityや「検索順位が高かったこと」はrelation真偽の証明に使わない。

ローカル三者合議

  • Primary=maxwell1500/ornith-35b:Q5_K_M、Challenger=gpt-oss:20b、Tie-break=gemma4:26bの既存Decision Routerを再利用する。
  • 2-of-3は真理/goldではなく、provenance付きsilver proposal。最終教師は実使用またはreview済みlocked eval。
  • artifactを生成したモデル自身の票を、同じartifactの独立検証票として数えない。producer除外またはrole rotationを必須にする。
  • 三者不一致、schema不正、timeout、model missing、evidence不足はheld。多数決で無理にpassしない。
  • 客観項目（source span存在、digest一致、未知page ID、矛盾、期限切れ）はモデル投票より先に決定論的vetoする。

先に固定するデータ契約

1. Relation event

各relation eventは少なくとも次を持つ。

  • relation_id（source/target/predicate/evidence digestから決定的生成）、event id、previous hash、schema/policy version。
  • source/target page UID・entity ID、predicate、direction、validity interval、status。
  • evidence span参照、source line、source raw/content digest。Dashboardには本文を渡さない。
  • extractor model/revision/template/rubric digest、confidence、producer role。
  • local consensus receipt、各vote digest、quorum、abstention/hold reason。
  • created/verified/used/retracted/stale timestampsと原因event。

2. Entity consolidation

  • mention、alias candidate、canonical entity、entity mergeを別型にする。文字列一致やembedding近傍だけでcanonical mergeしない。
  • DBSCAN系clusteringは候補生成のみ。cluster idはauthoritative entity idにしない。
  • 人名・製品名・モデル名・略称・同名異義を分離し、誤mergeをsplit/retractできるeventを持つ。
  • 既存Alias Store/PageRegistry/frontmatterを直接上書きせず、採用後にCAS/read-back付きの明示経路で同期する。

3. Rubric artifact

  • rubric_id/version、対象task、objective checks、subjective criteria、few-shot case refs、model/prompt digestを持つ。
  • 候補rubricはモデルがactive設定を直接編集せず、candidate artifactとして生成する。
  • 10/30件のdiverse labeled subsetで初期比較できるが、authority昇格には既存strong/gold・時系列holdout・非劣化gateを要求する。
  • 採用結果はDecision Router adoption artifact、Label Ledger、Recall Growth policy historyへhash-bindする。

実行手順

Phase 0 — Baseline、authority、不変条件を凍結

  1. GitHub HEAD、runtime archive、live config、model inventory、Field growth、co-fire、Recall calibration、search evalを再取得し、query本文を含まないsealed baseline manifestを作る。
  2. 現行 / Graphのみ / Rubricのみ / Graph+Rubricの四条件を同一query、同一candidate/token/deadline、同一time-ordered splitで比較するpreregistrationを固定する。
  3. 現行manual-94に加え、single-hop、multi-hop、global synthesis、entity ambiguity、alias collision、topic shift、hub false-positive、今回のような無関係カード誤注入を含むlocked fixtureを用意する。
  4. page labelとrelation/entity/rubric labelの母数・split・gateを分離し、relationの大量生成で既存strong positive数を水増しできないcontract testを先に書く。
  5. 外部API 0、同期4秒超過0、raw prompt/本文のruntime投影禁止、現行teacherをrollback先にする不変条件をmachine-checkableにする。

受入ゲート: 同じmanifestでbaselineを再実行でき、四条件の差分がfeature flagだけに帰属する。split leakage=0、外部model call=0をテストで証明する。

Phase 1 — Append-only Typed Knowledge Graph契約

  1. knowledge_graph/schema.pyへentity mention、entity candidate、relation event、community、consensus receipt、promotionのversioned schemaを追加する。
  2. knowledge_graph/store.pyへowner-only permission、file lock、idempotent append、hash chain、sealed snapshot、atomic replace、read-back、corrupt tail recoveryを実装する。
  3. relation IDとentity candidate IDをcontent/model/rubric digest込みで決定的にし、再実行で重複を増やさない。
  4. source content変更、page rename/archive/superseded、alias変更でrelationをstaleにし、再検証まで候補権限から除外する。
  5. 同じsource-targetでも複数predicate・複数根拠を失わないevidence bundleを実装する。既存TypedEdgeの後方互換出力は固定する。

受入ゲート: append-only chain、replay、idempotency、retract/split、content drift、同一target複数根拠、concurrent writer、corrupt recoveryが決定的。既存graph fixtureの出力はflag offでbyte-equivalent。

Phase 2 — RAGU型Graph Builderをsleep/backgroundへ追加

  1. changed page digestだけを対象に、Stage Aでentity mentionを抽出し、Stage Bで確定mention集合に拘束したrelationを抽出する。全relationにevidence span/source digestを必須化する。
  2. 既定producerをローカルモデルに限定し、JSON Schema、temperature/seed固定、context/token上限、prompt injection耐性、retry上限を既存structured callへ統合する。
  3. producer自身を独立reviewerとして数えない。重要merge/relationは残り2モデルまたは別role epochで検証し、no-quorumはheldにする。
  4. Graph Builderをsleep-cycleの独立laneへ追加し、foreground Recall、Semantic、Reranker、Ingest generation稼働中はpauseする。単一worker、queue上限、日次model-seconds/token上限、digest cacheを実装する。
  5. Meno-Lite-0.1は任意lab challengerとし、未導入でも本計画が完了するようにする。導入時も日本語/英語、Apple Silicon latency、relation precisionで既存モデルと比較する。

受入ゲート: 外部通信0。changed pageだけを一度処理し、同じdigestでmodel call 0。schema/evidence不備はproposedにすら入れない。foreground p95と4秒deadlineを非劣化。

Phase 3 — Entity consolidationとCommunity index

  1. casefold/Unicode/alias exact、Nemotron embedding、DBSCAN系clusteringを組み合わせてmerge候補を生成するが、cluster結果をauthorityにしない。
  2. entity mergeとrelation truthを別decision laneで判定し、同名異義、略称、モデルversion、人物/組織/製品衝突、誤merge splitをfixture化する。
  3. verified以上のgraphだけからLeiden communityをderived artifactとして作り、community membershipとsummary source refsを保存する。
  4. community summaryはローカルモデルで生成し、source page refs/digestsを必須にする。summary本文自体をgold evidenceにしない。
  5. incremental invalidation、community再編の安定性、巨大hub抑制、最大community/page/relation予算を実装する。

受入ゲート: 誤merge率、split復元率、unknown entity hold、community再計算の決定性をlocked setで測定。sourceを辿れないsummaryは検索候補に使わない。

Phase 4 — Typed GraphRAG candidate branchを既存検索/Fieldへ接続

  1. typed_neighbors()へrelation providerとstatus filterを追加し、既存callerを変更せずflag offの出力を維持する。
  2. query planをdirect/local/global/mixedへ分類する。simple exact queryは現行fast path、multi-hopのみrelation traversal、global questionのみcommunity候補を使う。
  3. relation pathにrelation IDs、predicate、direction、hop、evidence refs、lifecycle、各weight componentを残す。semantic verifyの結果をrelation真偽とは記録しない。
  4. 最初は独立shadow channelとして順位を変更せず比較する。candidate昇格後もverified以上だけを候補unionへ追加し、最終Page Certificateを必須にする。
  5. Fieldはproposed edgeを伝播しない。verifiedはcandidate bufferのみ、repeatedly_used以上だけpositive学習、authoritativeだけactive bufferへ許可する。
  6. per-predicate cap、degree normalization、hub penalty、cycle/self-edge防止、max hop/node/edge、deadline fallbackを適用する。

受入ゲート: shadowで現行順位・注入が不変。2-hop pathの全relation/evidenceを追跡可能。topic reset・低確信・store stale/corrupt時は即座に現行teacherへfallbackする。

Phase 5 — Local Consensus JudgeとRubric Calibration

  1. Decision Routerへrelation_verification、entity_merge_verification、recall_usefulness_judgment、recall_rubric_calibrationの専用lane/schema/prompt/contract casesを追加する。
  2. 客観判定（evidence support、contradiction、provenance、digest、unknown ID）は詳細rubric + deterministic checks、主観判定（必要性、marginal utility、topic relevance）は校正rubricへ分離する。
  3. zero-shot/current rubric、generated rubric、diverse few-shot、rubric calibrationを10/30件のcandidate setから比較する。MIPROv2/GEPAは同じgateに勝つ場合だけ任意採用する。
  4. case選択はrelevant、adjacent-but-unneeded、hub false positive、self-reference、topic switch、stale info、personal context、read-worthy、multi-hopを層化し、重複query/sessionを除く。
  5. 三者のmodel別precision/recall、ECE/Brier、abstention、pairwise error correlation、unanimous-wrong率、best-single比ensemble利得をlocked goldで測る。
  6. 採用rubric artifactだけを同期9B→35B Processorへロードする。同期Hookから20B/26B/35B三者を連続起動しないことをcontract testで固定する。

受入ゲート: 外部call=0、session/query leakage=0、各splitにpositive/negativeあり。false-passを悪化させず、best single modelをensembleが上回る。相関が高くensemble利得がない場合は現行rubricを維持する。

Phase 6 — Label Ledgerと既存自己成長ループへ統合

  1. 合議receipt、relation path、entity merge、rubric outcomeをprovenance付きLabel Ledgerへjoinし、subject_kindごとにcount/gate/splitを完全分離する。
  2. 単なるgraph exposure、candidate表示、合議passをstrongにしない。保存済みpathを経由したused pageだけrelation strong候補にする。
  3. 同じrelation pathが異なる実セッションで反復利用された場合だけrepeatedly_usedへ昇格する。retraction/negative feedbackは過去のpositiveを上書きせず対向eventとして残す。
  4. 既存Recall Growthへrelation/Judge品質gateを追加し、positive co-fire、typed relation weight、rubric採用を一つのpolicy history/LKG/rollbackで管理する。
  5. 200 strong / 20 sessions等の既存page gateは維持し、relation/entity/rubricは別々の最低母数・session分散・lower confidence boundをpreregistered evalから確定する。
  6. 実装後に手動で有効化する必要がないよう、データ成熟時はsealed gate→5/25/100%を自動進行し、悪化時は自動shadow rollbackする。

受入ゲート: label provenance join率100%、orphan/ambiguous receiptは棄却、page gate水増し0、policy history chain正常。再起動後も同じ成熟状態を復元し、将来の手動TODOを残さない。

Phase 7 — Cortex / Observatoryを関係グラフの実デバッガへ拡張

  1. 既存/cortexへrelation layer filter、lifecycle、predicate、direction、community、active path、consensusを追加し、新しい別画面は作らない。
  2. 右HUDにrelation ID、source/target、evidence ref、status、producer、三者vote/quorum、used count、promotion/hold/retract reasonを表示する。
  3. 静的relationは細いbase line/dashで表現し、黄色のtraveling electric arcは実Field spread eventだけに予約する。表示だけのedgeを発火に見せない。
  4. active nodeのサイズは変えず、既存halo/発光で示す。relation overlay、community hull、labelが重なって可読性を落とさないLODを実装する。
  5. ObservatoryへGraph Builder backlog/active model、relation counts by state、merge holds、community freshness、Judge disagreement/correlation、外部call=0、各rollout gateを追加する。
  6. projectionはbrowser-safeなID/digest/短いreasonだけにし、raw prompt、evidence本文、sensitive page metadataを渡さない。

受入ゲート: 実relation pathと表示edgeが1対1。発火eventなしで黄色arcを出さない。1280/1024/920/680pxで横overflow・枠外脱出・主要HUD重なり0、通常45fps以上、event-to-paint p95 ≤250ms。

Phase 8 — 四条件評価、canary、自動rollback

  1. 現行 / Graphのみ / Rubricのみ / Graph+Rubricを同一locked setで実行し、候補生成、rerank、certificate、commit、actual useの各stageを比較する。
  2. direct query、multi-hop、global synthesisを別集計し、単純検索の非劣化とmulti-hop改善を同時に要求する。
  3. Recall@5/10、MRR、used-page coverage、pointer/rich precision、negative-hit、abstention、誤merge率、relation path precision、p50/p95/max、4秒超過、memory/model-secondsを保存する。
  4. Graph+Rubricが単体施策より悪い場合は相互作用失敗として採用しない。全部不合格なら現行をwinnerとして記録する。
  5. sealed promotion artifactにmanifest、model/rubric/relation snapshot digest、全gateを含め、candidate→5%→25%→100%をsession hashで進める。
  6. drift、precision低下、false-pass増加、relation store stale/corrupt、model欠落、resource pressureで即shadowへ戻し、現行teacherを返す。

受入ゲート: 現行pointer/rich precisionとused-page coverageを非劣化、negative-hitを改善、multi-hop Recall@5を統計的に改善、4秒超過0、外部call 0。lower confidence boundとabstentionを併記し、0件注入だけでprecisionを稼ぐ構成を棄却する。

Phase 9 — 文書、GitHub runtime、live受入

  1. docs/architecture.md、docs/config.md、docs/operations.md、docs/hooks.mdへGraph Builder、relation lifecycle、local consensus、rubric、resource budget、rollbackを反映する。
  2. 各Phaseを意味のある単位でcommitし、完了直後に本計画のcheckboxと実行ログを更新する。既存の未追跡ファイルを混ぜない。
  3. push/restartの明示許可後、origin/mainへpushし、Dashboard、Semantic、Reranker、Ingest drain、必要なbackground workerをGitHub-backed runtimeから再起動する。
  4. runtime archiveのdirect_url commit、running process/module path、socket、status artifact、model inventory、Dashboard runtime commitをGitHub HEADと照合する。
  5. 実会話で現行検索とtyped graph candidateを発生させ、relation trace→Certificate→commit/reject→recall_used→Field event→Cortex表示を同じdecision/path IDで追跡する。
  6. Engineering CompleteとAuthority Maturityを別表示し、未達gate、現在値、目標値、自動再評価予定をDashboard/CLIへ残す。

受入ゲート: GitHub commit、全runtime archive、health、live Recall、live relation trace、Cortexが一致。ローカルworktreeだけでproduction完了と報告しない。

やってはいけないこと（必須）

  • 外部フロンティアモデル、クラウドJudge、外部embedding/APIをteacher・tie-break・fallbackとして呼ばない。
  • RAGUやMeno-Liteを現行検索の代替として一括導入しない。アーキテクチャをChronovisorの既存seamへ移植する。
  • 三者合議を同期UserPromptSubmitで毎回実行しない。4秒budgetとVRAM residencyを壊さない。
